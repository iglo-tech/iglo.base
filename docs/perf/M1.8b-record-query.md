# M1.8b record queries

First implementation of `RecordQuery` and the plain finders (`src/records/record-query.ts`), so there is no "before". The numbers put iglo.base's finders next to upstream PocketBase v0.41.0's list and view endpoints on the same data; later changes to this path compare against them, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-28 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Disk | the OS temp directory (`/tmp`, ext4) |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`) |
| Commit | `task/M1.8b-record-queries` |

## Method

`nice -n 10 bun test/records/bench-query.ts` after `bun run upstream:prepare`, with the host otherwise idle. A fresh upstream install gets a base collection `bench` (text `title`, number `n`, bool `active`) through `POST /api/collections` and 10,000 rows through `POST /api/sql`. Upstream's endpoints are timed first (HTTP round trips on 127.0.0.1 as a superuser, so request parsing, the handler, JSON encoding and the response are included). Upstream then stops and iglo.base's finders run in the bench process on a copy of the same `pb_data` (synchronous resolvers on the main-thread connection, rows hydrated into `Record`s, no JSON encoding). Each figure is the median of the runs (200, 10 and 50) after one warm-up run.

## Results

Two runs; the second in parentheses.

| Operation | iglo.base | upstream (HTTP) | upstream request |
|---|---|---|---|
| `findRecordById` | 0.06 ms (0.07 ms) | 0.78 ms (0.61 ms) | `GET /records/{id}` |
| `findAllRecords`, 10,000 rows | 36.4 ms (31.5 ms) | 208.5 ms (217.1 ms) | `GET /records`, 10 pages of 1,000 with `skipTotal` |
| `countRecords` with `active = true` | 0.80 ms (1.14 ms) | 4.11 ms (4.31 ms) | `GET /records?filter=active=true&perPage=1` (`totalItems`) |

- The two sides do not do the same amount of work: upstream's figures include HTTP, the API rules, the field resolver and JSON encoding, and its count request also reads one row. They show that the query and hydration path is not the bottleneck; the API tasks (M2.4) measure endpoint against endpoint.
- Hydrating 10,000 records (about 3.5 µs each) is the bulk of `findAllRecords`: every row becomes a NullStringMap and goes through each field's `prepareValue`, as upstream does.
