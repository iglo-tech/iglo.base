Every capped case is one name: the filter reads `@request.query.perPage`, so a companion with another page size would ask a different question. Those keep only the page-size check. The other caps never fired: over 1,000 matches, a companion refused, no room for an id key at 8 sort terms.

No real difference was found, so no fix went into `src/`, there are no before/after costs, and `regressions.ts` has no `fixed` entries yet (it holds 17 boundary cases). There are no exclusions.

## Detection

A clean run only counts if the fuzzer can fail. Faults were put into `src/` one at a time, then removed. Multi-match removed for `!=` in `src/search/filter.ts`: 1,500 cases gave 4 distinct failures, each shrunk to one condition (`@collection.users.name != ""`). A one-key sort without an id reversed: 14 distinct failures in 1,500 cases. The list rule skipped when `skipTotal` is present: 6 in 1,500. `fuzz.test.ts` also substitutes responses: a superuser page for a guest page, `sort=-id` for `sort=id`, a record from outside a tie. A separate 30,000-case exploratory run, which also required the same order for every list and equal item bodies, found no difference.

## Method

- **Data:** upstream's fixture on one copy per server. Upstream's API sets four list rules first (`demo1`, `demo2`, `numeric_id_view`, `view2`), giving relation, auth-relation, header and `@collection` rules beside the fixture's null, `""` and field rules. It also creates `fuzz_items` and `fuzz_tags` (`test/differential/fuzz/data.ts`), because the fixture has no stored `%`, `_`, `\` or non-ASCII text, no JSON scalars, no large or fractional numbers, no dangling relation, and no data behind a unique single back-relation.
- **Order:** classified from the sort text sent, with the model (`classifySort`). Total: an `id` or `@rowid` key before any multi-row key; ids compared in order. Own-row: all keys on the record's row or through single relations; two companions fetch the full result with `,id` and `,-id` appended, both compared in order, and each page must match its own server's full result position by position, up to groups of ties (a record's place differs between the two only inside a tie). Multi-row: a multiple relation, back-relation or `:each` anywhere in a key; a companion with the same sort compares the full id sets, and each page must be a subset of its own server's set. SQLite's choice among duplicates is not defined there, so these stay set-only. Companions also compare totals, including for `skipTotal` requests. A list of at most one record that holds every match needs no companion and counts as exact.
- **Fixed values:** generated records' `created` is written as a fixed value before the copies are made; the generated collections have no `updated`, and the fixture's autodates end in 2025. The test prepares two fixtures independently and compares the model and the requests of seed 1001, cases 0–999.
- **Clock:** `@second` and `@minute` appear only in comparisons that hold at any instant (`@second < 60`). Other macros and current-time `strftime` are marked time-dependent, and a difference on such a case is retried once; neither seed needed a retry. `strftime` of the current time uses formats no finer than a day, because finer ones race with `@now` inside one server: one early run reported `strftime("%Y-%m-%d %H:%M:%f") <= @now`, which flipped in both directions and is not a server difference.
- **Throttle:** upstream's randomized list throttle applies on both servers and is part of the durations above.
