# M7.1b: log writer thread and the low-risk list-path fixes

Fixes #1, #3, #4 and #5 of the [M7.1a report](M7.1a-profile.md) §3, with the numbers before and after and a new profile for M7.1c. Results of the API are unchanged (the existing suites and the new tests below pass).

## What changed

| # | Fix | Where |
|---|---|---|
| 1 (D31) | The `_logs` batch insert runs on a log writer thread with its own `auxiliary.db` connection. The main thread builds the rows (`logDBExport`) on the event loop, as before, and posts them. A held lock is waited for (busy_timeout 10 s, then upstream's retry intervals, 12 tries); the app stop blocks until the thread acknowledged the batches (a `SharedArrayBuffer` counter), so a flush at SIGTERM, after a restore and in every CLI command that logs is kept. Backup and restore call `logger.suspend()` (drain, close the connection, end the thread) before they touch the files and `resume()` after; logs taken meanwhile wait in memory. | `src/logs/log-writer.ts`, `log-worker.ts`, `logger.ts`, `src/backups/create.ts`, `restore.ts`, `package.json` build, `src/db/connect.ts` (`openReadWrite`) |
| 3 | `parseDateTime` reads `YYYY-MM-DD HH:MM:SS.mmmZ` by position; anything else, and any field out of range, goes to the Go layout parser as before. | `src/tools/types/datetime.ts` (`parseDefaultLayoutFast`) |
| 4 | An `All` read on the read pool sends the column names once and an array per row; the main thread builds the row objects (`rowsFromValues`, last duplicate column wins, `__proto__` an ordinary key). `one`, `row` and `column` reads are unchanged. | `src/db/read-pool.ts`, `read-worker.ts`, `src/db/dbx/rows.ts` |
| 5 | Hydration builds the record without the `NewRecord` default pass (every field was prepared twice), without the intermediate `NullStringMap` of all columns, and creates the `#data` and `#customVisibility` stores on first write. | `src/records/record-model.ts`, `record-query.ts` |

Not done: the JSON writer (#2), expand driver (#6), per-request overhead (#7), startup (#8).

Tests added: `test/logs/log-writer.test.ts` (lock held by the main thread: the batch waits and is written after the commit; stop and restart of the thread; a backup taken while logs are written has an `auxiliary.db` that passes `integrity_check`; logs written before SIGTERM are in `_logs` after the compiled executable exits), the corpus and random comparison of the fast date path with the Go layout parser in `test/tools/types/datetime.test.ts` (about 20,000 strings: the fast path returns exactly what the slow parser returns, and null exactly where it fails), and a pool-against-main-thread comparison of `All` rows (exact integers and narrowed, BLOB, NULL, REAL infinities and -0, duplicate column names, `__proto__`, integer-like names, PRAGMA, empty result) in `test/db/read-pool.test.ts`. The `settle` helper of `test/apis/logs.test.ts` now also waits for the writer thread.

## What each fix does, from the profiles

- **#1** is the one that shows in the numbers: `/api/health` at 50 clients 4,252 → 9,396 req/s (p50 6.65 → 4.79 ms), at 8 clients 4,844 → 5,929. The `commit` and the insert loop (39% of the main thread in M7.1a) are gone from it; what remains of the log path on the main thread is building the rows and the `postMessage` (next section).
- **#3**: `parseDateTime` of a stored date fell from 15.3% of the list profile to about 1% (`parseDefaultLayoutFast` 1.1% self).
- **#4**: a worker hop moves less data, but `postMessage` is still the largest single self time of the list profile (below), because the cost is per message, not per byte. The structured clone of the rows is no longer the driver: microbenchmark of one 30-row result (10 columns, 1 KB body), main-thread CPU per result: object per row 120–139 µs, columns once + arrays + object rebuild about 115, arrays only 86–113, JSON text + parse 70–88. Arrays were chosen because JSON text cannot carry bigints (exact integers) or BLOBs; the rebuild keeps the rest of the code unchanged. The gain is small and inside this host's noise.
- **#5**: `hydrateRecord` 3.3% self and 10.1% for the hydration area (it was 24% total with the date parse); `Object.entries` (3.1%) remains from other callers (`publicExport`, `fieldsData`).

## Ranked for M7.1c

1. **JSON writer for record lists (#2)**: still the largest area on list and expand (18 to 28% self, 32 to 42% total). Unchanged first place.
2. **Cost of the read-pool hop**: 21% of the list profile is the main-thread `postMessage` per read, a per-message cost. Options: fewer messages per request (one message for a batch of reads, such as the expand levels or count + list), or a cheaper channel; check whether the first-use of `MessageChannel` ports or `Atomics`-woken shared memory is cheaper before building it.
3. **Log row export on the main thread** (32% of `/api/health`): the Go-compatible JSON of the attrs. It cannot simply move to the worker (attrs hold Error objects and class instances such as DateTime and Float64 that a structured clone would flatten), but the request log's attrs are a fixed shape and can be written by a dedicated string builder; and `logSQL` and other debug-level strings should not be built when the level is off.
4. Per-request overhead (#7): the health profile is 31% routing and response building; an `Error` object per create request.
5. Expand driver (#6) and `Object.entries` in `publicExport`/`fieldsData`.
6. Startup (#8): unchanged, 240–290 ms against 52 ms (the log writer thread starts with the first batch, not at start).

If the 50-client bar for create and expand still fails after 1 to 3, the rest is single thread against many cores, as M7.1a said.

## Local checks

`bun run check`: 18,296 tests, 0 failures. `bun run test:reference`: 4,399 pass, 2 fail, both passing on two reruns alone: `apis/sql_test.go TestSQLRun > query with length equal to the limit` (`execTime` 1 against 0 ms: a timing value, the host was loaded) and the realtime differential `a user delete updates the records that reference it` (two update events arrived in the other order). Neither involves hydration or the log path.

The first full reference run found a real bug in #4: the roundtrip differential (`test/differential/roundtrip`) failed on a column added by a collection update (`note_b` read as missing, then as a stale value). A cached pool statement re-prepares after a schema change, but `columnNames` is current only after the statement ran; the pool had read the names before. `Rows` now takes the names after `values()`, `all()` and `get()` (the last two had the same stale `narrowRow` names), and `test/db/read-pool.test.ts` covers an added column.
