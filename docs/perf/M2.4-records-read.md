# M2.4 records list and view

First records endpoints, so there is no "before". Later changes to the read path compare against these numbers, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Upstream | PocketBase v0.41.0 release binary (Go 1.27.2) |
| Commit | `task/M2.4-records-read` |

## Method

`nice -n 10 bun test/perf/records-read/bench.ts --concurrency <n>`, with the host otherwise idle. The script builds one fresh install through upstream's API: 10 teams, 50 members (auth, `team` relation), and 200 posts (`title`, an editor `body` of about 180 bytes, `views`, `author` relation, `created`) in two collections with the same records: `posts` (list and view rule `""`) and `posts_rel` (rule `author.team.name != "Team 3"`, a two-join relation rule). Upstream and the iglo.base executable then each serve a copy of that pb_data in turn (iglo.base with its default read worker pool). Every workload runs as a guest over keep-alive `fetch` connections: 300 warm-up requests, then 3,000 requests with `n` in flight. The client is Bun on the same machine, so it shares the CPU with the server.

## Results

Requests/s, p50 and p99 latency.

| Workload | Upstream, 1 in flight | iglo.base, 1 in flight | Upstream, 8 | iglo.base, 8 | Upstream, 50 | iglo.base, 50 |
|---|---|---|---|---|---|---|
| list 30 | 776/s, 1.08 / 3.28 ms | 684/s, 1.19 / 3.72 ms | 3,660/s, 2.05 / 5.20 ms | 1,090/s, 6.14 / 20.99 ms | 3,724/s, 9.6 / 64 ms | 958/s, 52 / 94 ms |
| list 30, relation rule | 556/s, 1.53 / 4.05 ms | 580/s, 1.40 / 4.46 ms | 2,446/s, 3.15 / 6.93 ms | 957/s, 6.87 / 24.24 ms | 2,726/s, 13.5 / 73 ms | 882/s, 57 / 91 ms |
| list 30, expand `author.team` | 200/s, 4.77 / 7.36 ms | 256/s, 3.23 / 8.47 ms | 1,482/s, 5.14 / 10.36 ms | 373/s, 18.8 / 51.8 ms | 1,669/s, 21.9 / 115 ms | 386/s, 126 / 210 ms |
| view | 1,523/s, 0.67 / 1.41 ms | 1,621/s, 0.56 / 1.18 ms | 13,320/s, 0.52 / 1.86 ms | 6,530/s, 1.03 / 4.46 ms | 17,475/s, 2.3 / 10.2 ms | 6,904/s, 6.8 / 17.7 ms |

- One request at a time, iglo.base is within about 10% of upstream, and ahead with expand and view.
- With requests in flight, upstream spreads them over the 6 cores; iglo.base runs everything except the SQLite statements on its one event loop, so its throughput stops at about 1,000 lists/s and latency grows with the queue. At 50 clients the list p50 is 5× upstream's; the design's bar (02-architecture.md: p50/p95 within 1.5× at 50 clients, checked for 1.0 in M7) is not met yet.
- In-process, a 30-record list costs about 0.8 ms in the query (read pool round trip, rows to Records) and 0.2 ms in the JSON. The JSON is written straight from the records' own encoding (the search result and `Event.json` no longer re-format it; that brought the list JSON from 0.63 to 0.2 ms). With a 2-level expand the JSON takes about 1 ms, because `Record.marshalJSON` re-formats the JSON of each expanded record at every nesting level (`src/records/record-model.ts`, `src/tools/types/go-json.ts`; not changed here).
