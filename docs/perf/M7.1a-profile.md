# M7.1a: performance profile and async bcrypt

iglo.base against upstream PocketBase v0.41.0, measured on one host with the same data. This report is the input for M7.1b. Nothing here changes the API or data contracts.

## Setup

| | |
|---|---|
| Date | 2026-11-02 |
| Host | AMD Ryzen 5 1600 (6 cores), Linux 6.12, VM with dynamic memory (MemTotal 15.6 GiB); **shared with other agents' builds and tests**: the load average was 4 to 9 during the runs |
| Bun | 1.4.4 |
| iglo.base | `bun run build` (compiled), main at 7edd229 plus this change |
| Upstream | v0.41.0 release binary from `bun run upstream:prepare` |
| Load tool | `test/perf/compare/bench.ts`: fetch over keep-alive connections from a separate Bun process, one server at a time, 1.5 s warm-up excluded, 4 s measured per cell, 3 repetitions (a fresh copy of the data and a fresh server each), median reported. The load generator's CPU time is printed per run (about 1 to 3 s of CPU per 4 s at the health workload; it is a single JS thread and can limit the health numbers of the faster server) |
| Data | built through upstream's API: a superuser, 20 teams, 200 `members` (auth, default bcrypt cost 10, relation to a team), 3,000 `posts` (title, 5 × paragraph editor body, number, author relation, autodate). The vendored fixture is not written to. Guest rules are empty, so guests can list, view and create posts |

Commands (one at a time):

```sh
bun run upstream:prepare && bun run build
nice -n 10 bun test/perf/compare/bench.ts --keep <dir>/pb_data        # the table below
nice -n 10 bun test/perf/realtime/measure.ts                           # M5.1's bench
nice -n 10 bun test/perf/compare/bcrypt-lag.ts --exe before=<exe>,after=dist/iglo-base --upstream
nice -n 10 bun test/perf/compare/bench.ts --keep <dir>/pb_data --target iglo-base --repeat 1   --seconds 8 --clients 50 --workloads list --cpu-prof <dir>/prof      # one profile per workload and client count
bun test/perf/compare/summarize-profile.ts <file>.cpuprofile
```

**Noise is high.** The host was shared, so the same cell varied between repetitions: the spread of the three req/s values (max − min over the median) had a median of 30% for iglo.base and 49% for upstream, up to 110% and 144% in single cells. Only differences far larger than that mean anything. The conclusions below rest on the large effects (the request log, JSON writing, hydration), which show in both the profiles and the logs-off experiment.

At 1 client every p50 is within 1.4× except expand author.team (1.37, within) and the filter + sort list is faster. The gap opens with concurrency: upstream serves reads on several cores, iglo.base's JavaScript runs on one thread (the owner dropped multi-thread serving), so req/s at 8 to 50 clients is 0.5 to 0.7× on the read and write workloads, and 0.36 to 0.6× on `/api/health`. Password auth is bound by bcrypt on both (46 against 44 req/s at 8 clients).

### Startup, idle memory

iglo-base: startup 264/405/217 ms (median 264), idle RSS 78.7/78.6/79.1 MiB (median 78.7), RSS after the run 184/188/171 MiB
upstream: startup 53/52/52 ms (median 52), idle RSS 37.0/35.0/35.0 MiB (median 35.0), RSS after the run 178/389/287 MiB

Startup is the time from spawn until `/api/health` answers (iglo.base polled every 5 ms, upstream's helper every 50 ms, so upstream's real figure is at most its 52 ms). Idle RSS is 3 s after start. iglo.base's extra ~45 MiB at idle is the Bun runtime with the read worker pool (each worker holds its own SQLite connection and module graph); the compiled binary is 114 MB against 33 MB. Startup is dominated by loading the module graph (a profile of `bun src/main.ts serve` shows `node:fs/promises` 18%, `node:http` 13%, the first collections cache load 13%, regexp compilation at start 9.5% of 490 ms).

## 4. bcrypt off the event loop (D27)

Hashing and verification now run on Bun's thread pool (`Bun.password.hash` / `verify`) and keep Go's `$2a$` hash form:

- `src/tools/crypto/bcrypt.ts`: `generateFromPasswordAsync`, `compareHashAndPasswordAsync` (the parse and checks are shared with the synchronous forms through `prepareCompare` and `checkGenerate`; the rare non-canonical-salt hash still verifies on the calling thread with Go's computation).
- `src/fields/password.ts`: setting a password starts the hash (argument errors such as the 72-byte limit and invalid cost are recorded at once, as before) and the field's first record interceptor waits for it, outside any transaction. A save inside a transaction (a batch, a migration file, the sync entry points) computes a still-pending hash on the calling thread first (`settleHashesSync` in `src/records/record-save.ts`), so the transaction stays synchronous (D8, D28). Reading `hash` while it is pending computes it synchronously as a safety net.
- `recordCreate` waits for the hash before it exports the dummy record for the create rule check (`settlePasswordHashes`); this path read the hash and had kept the create blocking.
- Verification: `auth-with-password` (and its dummy check for an unknown identity) and `auth-with-otp` use `validatePasswordAsync`. Left synchronous: the old-password check in the record upsert form and the password check in the email change confirm form, because they run inside the validation library's synchronous `By` rules; they run only on those two rarely used requests and are a candidate for M7.1b.

Event-loop wait, 8 concurrent cost-12 operations while `/api/health` is requested one after another (5 repetitions, `test/perf/compare/bcrypt-lag.ts`; "before" is main at 7edd229):

| Server | Operation | operation p50 / max ms | 8 at once, wall ms (median) | health requests | `/api/health` p50 / p95 / max ms |
|---|---|---|---|---|---|
| before | 8 × sign-in | 1220 / 1972 | 1955 | 33 | 0.8 / 1951.2 / 1972.4 |
| before | 8 × create | 2455 / 3947 | 3918 | 33 | 0.7 / 3917.7 / 3943.3 |
| after | 8 × sign-in | 503 / 777 | 671 | 490 | 0.4 / 6.7 / 27.6 |
| after | 8 × create | 753 / 1194 | 1074 | 798 | 0.3 / 6.0 / 19.4 |

The `/api/health` max latency during 8 sign-ins falls from about 2 s to 28 ms, and during 8 creates from 3.9 s to 19 ms (p95 from 3.9 s to 6 ms). Sign-in time at 8 at once drops from 1.2 s to 0.5 s p50 (8 bcrypt computations on 6 cores in parallel, as upstream). The one-at-a-time cost is unchanged. Hashes written by either server verify on the other: the 158 cross-server checks of M0.8 are covered by `test/tools/crypto/bcrypt.test.ts` and the reference differential suite; `test/tools/crypto/bcrypt-async.test.ts` adds the async forms and an event-loop check.
