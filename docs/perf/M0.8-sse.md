# M0.8 spike: 1,000 SSE connections

Is a `Bun.serve` response with a `ReadableStream` body fit for M5.1's realtime broker, and which limits must M5.1 set? Measured with a throwaway server, compared with upstream's `/api/realtime`.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, about 8 GiB available during the runs) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary |
| Commit | `task/M0.8-spikes` |

## Method

`nice -n 10 bun scripts/spikes/M0.8/sse.ts`.

`scripts/spikes/M0.8/sse-server.ts` is a throwaway Bun server, not M5.1's broker. Its `GET /api/realtime` returns a `ReadableStream` with a `ByteLengthQueuingStrategy` (64 KiB high water mark), sets upstream's headers (`text/event-stream`, `Cache-Control: no-store`, `X-Accel-Buffering: no`) and first sends `PB_CONNECT` with a 40-character client id. It uses upstream's framing, `id:<clientId>\nevent:<name>\ndata:<data>\n\n` (`tools/subscriptions/message.go`). `POST /broadcast` enqueues one framed message per client, as upstream writes the client id into each message. The server runs in three modes:

- **default:** Bun's default `idleTimeout`, 10 s.
- **idleTimeout 0:** `idleTimeout: 0` for the whole server.
- **timeout(req, 0):** the default, plus `server.timeout(req, 0)` on each realtime request only.

On upstream the clients subscribe to `notes/*` (list rule `""`), and a broadcast is a record create in `notes`. Upstream's latency therefore includes the create and the rule check for each client.

The clients are raw sockets in one Bun process, which parses every stream. Latency runs from just before the broadcast trigger is sent to each client's receipt of the event. It includes the client's own parsing of 1,000 streams, the same for every server.

Phases, each on a fresh server:

1. Open 1,000 connections, 50 at a time, each waiting for `PB_CONNECT`.
2. Stay idle for 15 s.
3. Send 20 broadcasts with 64 B of data, then 5 with 16 KiB, 200 ms apart.
4. Close 400 clients with a TCP reset and 400 with a FIN, then broadcast once to the 200 left.
5. Keep 10 clients. One stops reading (`socket.pause()`), then 400 messages of 64 KiB (25 MiB) are broadcast. Then it reads again.

RSS and open file descriptors come from `/proc/<pid>`.

- **Idle timeout:** Bun's default `idleTimeout` (10 s) closed every idle SSE stream after 10.3 s and logged `Bun.serve() timed out a request after 10 seconds`. Upstream keeps a realtime connection for 5 minutes without messages and at most 30 minutes in all (`apis/realtime.go`: `IdleTimeout`, `MaxTimeout`). Bun's `idleTimeout` cannot go above 255 s. `server.timeout(req, 0)` on the realtime request alone keeps the streams open and leaves the 10 s default for every other request.
- **Disconnects:** the stream's `cancel()` ran for every client that went away, whether by RST or FIN (801 cancels, counting the warm-up), without needing a write first. File descriptors were back to 207 within 2 s, and no `enqueue` failed. Upstream also notices a closed client at once, through the request context.
- **Backpressure:** neither server bounds what it holds for a client that does not read. In Bun the stream queue grew to 21.9 MiB, and the rest of the 25 MiB sat in kernel socket buffers; `controller.desiredSize` reports it (−21.8 MB). Upstream's `Client.Send` blocks on an unbuffered channel inside one `routine.FireAndForget` goroutine per message. Its write has no deadline (`SetWriteDeadline(time.Time{})`), and the idle timer cannot fire while a write is blocked. Both delivered everything once the client read again.
- **Broadcast cost:** one 16 KiB broadcast to 1,000 clients enqueues 16 MiB, since every message carries its client id. RSS rose to 76–96 MiB and came back down. Encoding the shared part once and sending the `id:` line as a separate chunk would avoid copying it per client.
- **File descriptors:** both servers use one per connection. Bun raises the soft `RLIMIT_NOFILE` to the hard limit at start, as Go does: with `ulimit -Sn 1024`, `/proc/self/limits` showed 524288 under Bun. The number of realtime connections is therefore bounded by the hard limit of the service.

## Answer

`Bun.serve` with a `ReadableStream` per client is fit for M5.1. It holds 1,000 idle connections in 18 KiB each, against upstream's 61 KiB. Broadcast latency matches upstream's or is better: p50 about 11 ms and p99 about 30 ms for 1,000 clients, against upstream's 15 ms and 36 ms. It notices abrupt disconnects at once and releases their descriptors.

M5.1 must set these limits:

1. `server.timeout(req, 0)` on the realtime request. Without it Bun closes every idle stream after 10 s, where upstream keeps it for 5 minutes. Keep the server-wide default for other requests.
2. Upstream's own timers in the broker: close the stream (`controller.close()`) after 5 minutes without a message and after 30 minutes in all, and unregister the client in `cancel()`.
3. A queuing strategy that counts bytes (`ByteLengthQueuingStrategy`), with `desiredSize` checked after each enqueue.

**Proposal for M5.1 (lead decides):** close a client whose queue goes over a cap; 8 MiB is suggested. Upstream holds an unbounded amount for such a client, in blocked goroutines, and delivers it all if the client ever reads again. A cap changes that only for clients that stop reading. The JS SDK reconnects and subscribes again after a dropped connection. If the lead takes it, it is a deliberate difference to list in `docs/design/04-api-compatibility.md`; the alternative is to match upstream and accept unbounded memory per stuck client.
