# M2.2 resolver: record field resolver and filter record queries

First implementation of the record field resolver (`src/resolver/`), `FindRecordsByFilter` and `CanAccessRecord` (`src/records/record-query-filter.ts`), so there is no "before". Later changes compare against these numbers, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Commit | `task/M2.2-record-field-resolver` |

## Method

`nice -n 10 bun test/resolver/bench.ts`, with the host otherwise idle; each figure is a median.

- **Resolve + build:** a new resolver, `filterBuildExpr` (every field resolved, the joins and multi-match subqueries), `UpdateQuery` and the SQL text of the record query, on a copy of the vendored fixture, with a `users` auth record in the RequestInfo. "Rule" builds with hidden fields allowed (as rules are); "guest filter" without (as a guest's client filter, which adds the list-rule joins). 2,000 runs after 200 warm-up runs, no parse cache.
- **List with a relation rule:** 10,000 books, each with one of 100 authors (no index on the relation column), with the list rule `author.active = true && author.name != 'author 3'` (5,000 rows visible). A guest's list follows records list's steps: the rule on the record query, the Provider with the resolver, `sort=-title`, page 1 of 30 with the count query. Also with a client filter through the relation, and `CanAccessRecord` for one record with the same view rule. On the main-thread connection and through the read worker pool (2 workers); 50 runs after 5 warm-up runs (500 after 50 for `CanAccessRecord`).

## Results

Two runs; the second in parentheses.

| Rule (collection) | Rule | Guest filter |
|---|---|---|
| simple: `title = 'test' && @request.auth.id != ''` (demo4) | 0.060 ms (0.059 ms) | 0.056 ms (0.050 ms) |
| 3-level relation: `self_rel_one.self_rel_one.self_rel_one.title = 'test'` (demo4) | 0.049 ms (0.053 ms) | 0.043 ms (0.044 ms) |
| back-relation: `demo4_via_rel_one_cascade.title ?= 'test'` (demo3) | 0.174 ms (0.179 ms) | 0.177 ms (0.173 ms) |
| `@collection` with an alias (demo4) | 0.074 ms (0.064 ms) | 0.071 ms (0.069 ms) |
| `:each` over a multiple relation: `self_rel_many:each = 'abc'` (demo4) | 0.064 ms (0.057 ms) | 0.076 ms (0.066 ms) |
| auth relation: `@request.auth.rel.title != ''` (demo4) | 0.051 ms (0.050 ms) | n/a (users is superusers only) |

| List over 10,000 rows | Main thread | Read pool |
|---|---|---|
| guest list with the relation rule, page 1 of 30, with count | 10.65 ms (11.05 ms) | 8.37 ms (8.48 ms) |
| the same with `filter=author.name ~ 'author 1'` | 7.51 ms (7.67 ms) | 4.54 ms (4.68 ms) |
| `CanAccessRecord` | 0.107 ms (0.120 ms) | 0.193 ms (0.240 ms) |

- Resolving and building a rule stays well under a millisecond. The back-relation case is the slowest because it parses the back collection's indexes for a single-column unique index on each resolve, as upstream does.
- The list cost is SQLite running the join, the count and the page; the resolver's part is a few hundredths of a millisecond. On the read pool the count and the page run on two workers at once.
- A single `CanAccessRecord` is a one-row lookup; through the pool the message round trip to the worker costs about 0.1 ms more than the query.
