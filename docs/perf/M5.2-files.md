# M5.2: file serving and thumbnails against upstream

Does `GET /api/files/...` serve what upstream v0.41.0 serves, with thumbs that match upstream's, with bounded memory? Two measurements: the differential suite through the HTTP API (the M0.7 compatibility set among its cases) and the memory of the thumb generation and of a large download, one case at a time.

## Thumbs through the HTTP API

Upstream stores every test file through its records API (collection `m52`, one record per file) on a copy of the vendored fixture; both servers then serve their own copy of that `pb_data` (same stored names, bytes, `.attrs` and modification times). The images are the M0.7 generator's (`test/differential/files/images.ts`): one image per format, the whole M0.7 compatibility set (EXIF orientations 1–8 in both byte orders, XMP before and after the Exif segment, a GIF whose first frame is smaller than its logical screen, and the originals at `PB_THUMBS_MAX_SOURCE_PIXELS` = 1,000,000, served by a second pair of servers started with that limit) and the M0.7 edge set (damaged files). The sizes are the field's `thumbs` (`50x50`, `50x50t`, `50x50b`, `50x50f`, `0x40`, `40x0`, `300x300f`, and `70x50f`, `0x50` for the limit cases) plus the default `100x100`; `33x33`, `0x0` and `100x100f` are not listed and must serve the original.

For every request both servers must take the same branch (thumb or original). A thumb must have the same status, `Content-Type`, `Content-Disposition` and CSP, the same dimensions, a mean absolute error per channel within the tolerance below, and a stored `.attrs` equal to upstream's apart from the MD5 of its own bytes. An original must be byte-identical with the same headers.

- **Outcome, dimensions, content type:** equal for all 214 thumb requests of the run (162 thumbs, 52 originals), and the stored thumbs' `.attrs` match upstream's (`user.content_type` as `createThumb` sets it, `user.metadata` `{}`).
- **Pixels:** PNG, GIF and lossless WebP originals give identical thumbs (MAE 0). JPEG thumbs differ by at most 1.78/255 per channel (the decoders: libjpeg-turbo against Go's image/jpeg; M0.7 measured about 1/255 on its photo set). Lossy WebP differs by up to 8.53/255 (libwebp against x/image/webp; M0.7 measured 5–8/255). The tolerances are those of M0.7's answer; a pixel match for lossy WebP would need a port of x/image/vp8 (D10 backlog).
- **Limits:** the originals over 1,000,000 pixels (by the size Go's `image.DecodeConfig` reads: the GIF's logical screen, the JPEG before its orientation, the WebP's VP8, VP8L or VP8X size) serve the original on both servers; the ones at the limit get thumbs.
- **Damaged files:** every edge-set file serves the original on both servers, except the two D26 backlog cases M0.7 found (`cut-scan-eoi.jpg`, a JPEG cut in its scan data and followed by EOI, and `no-iend.png`), where upstream serves the original and iglo.base a thumb. The suite checks upstream's outcome for these two and does not compare them.
- **Thumbs cached by the other server:** a thumb (with its `.attrs`) stored by upstream and copied into iglo.base's storage is served by iglo.base byte for byte with upstream's content type, and the reverse.

The rest of the suite (originals of every type with their `Content-Type`, `Content-Disposition`, CSP and `Cache-Control`; `download=1/true/0/yes`; `HEAD`; single, suffix, open, multiple, unsatisfiable, malformed and oversized ranges; `If-None-Match`, `If-Match`, `If-Modified-Since` in the three date formats, `If-Unmodified-Since`, `If-Range` with an ETag or a date; missing collection, record, file in the record and file on disk; protected files with user and superuser file tokens, tokens from either server, expired, wrong-collection and forged file tokens, auth tokens in the query and in the `Authorization` header) compares the status, the headers and the bytes: all equal. 145 cases, plus two large-file cases (below).

## Memory

`test/perf/files/measure.ts`: upstream stores a generated 50-megapixel JPEG (8660×5774, q90) and a 160 MiB file; each case runs on a fresh server and a fresh copy of that `pb_data`. RSS before is `VmRSS` one second after the start; the peak is `VmHWM` after the case (the whole process, the thumb worker threads included). Every response was checked to be the thumb (or, for the download, the file).

| Case | Server | Status (served) | RSS before (MiB) | Peak RSS (MiB) | Peak − before | ms |
|---|---|---|---|---|---|---|
| 50 MP JPEG thumb, c=1 | upstream | 200 thumb | 35 | 237 | 201 | 647 |
| 50 MP JPEG thumb, c=1 | iglo.base | 200 thumb | 78 | 109 | 31 | 182 |
| 50 MP JPEG thumbs, c=4 | upstream | 200 thumb,200 thumb,200 thumb,200 thumb | 33 | 730 | 697 | 1076 |
| 50 MP JPEG thumbs, c=4 | iglo.base | 200 thumb,200 thumb,200 thumb,200 thumb | 77 | 290 | 214 | 342 |
| 160 MiB download | upstream | 200 original | 33 | 34 | 0 | 144 |
| 160 MiB download | iglo.base | 200 original | 77 | 85 | 7 | 188 |

- **50 MP JPEG thumb:** +31 MiB at one in flight against upstream's +201 MiB, and +214 MiB at four in flight against +697 MiB. An original over 16 MP is reduced by `Bun.Image` while it decodes (libjpeg-turbo decodes a JPEG at a DCT scale), so its full pixels never exist in the worker (D10). Each generation runs in its own lazily started worker (about 4 MiB each when idle, stopped after 30 s idle); `PB_THUMBS_MAX_WORKERS` (default NumCPU + 2) caps how many run at once, as upstream's semaphore does. Originals up to 16 MP take the exact path, about 23 bytes per source pixel in the worker (M0.7), so at most about 370 MiB per generation.
- **160 MiB download:** +7 MiB, against upstream's +0. The file is a Blob of the stored file that Bun streams to the socket; it is never read into memory. iglo.base's higher RSS before (77 MiB against 33 MiB) is the Bun runtime and the embedded dashboard, as in M3.2.
- **Multipart ranges:** a `multipart/byteranges` body is put together in memory up to 16 MiB. A larger one cannot be streamed with its `Content-Length` in Bun 1.4.4: `Bun.serve` sends every JavaScript `ReadableStream` chunked and drops a set `Content-Length`, and a `Blob` built from `Bun.file` slices loses their bytes (probed: a `new Blob([bytes, file.slice(…), …])` of three 20-byte strings and two 30 MB slices has size 25). Bun sends the `Content-Length` only for a Blob it can size, so the parts are copied in 1 MiB pieces into a file in `pb_data/.pb_temp_to_delete` (the temp directory upstream clears at start; iglo.base clears it too), sent as that file's Blob, and the file is unlinked once Bun has opened it (the response finishes from the open file). `HEAD` computes the length without the copy. The body and `Content-Length` equal upstream's (differential case below). The cost is a temporary copy of the requested ranges on disk per such response, at most the file's size, since ranges adding up to more than the file are ignored as in Go.
- **Large-file regressions** (`test/files/file-api.test.ts`; the peak is `VmHWM` after `clear_refs` 5 just before the request, on a server already warmed up by one request):

  | Case | Response | Peak − before |
  |---|---|---|
  | `?thumb=111x111` on a valid 4000×2000 PNG of 24.0 MB with `PB_THUMBS_MAX_SOURCE_PIXELS=1000`, `Range: bytes=0-0` (so the served original stays out of the measurement) | 206, the original's first byte, no thumb stored | +0.6 MiB (+26.2 MiB before this fix, which read the whole original before the header check) |
  | `Range: bytes=0-9437183,10485760-19922943` on a 24 MB file | 206, 18,874,710 bytes with `Content-Length` equal to `HEAD`'s, no `Transfer-Encoding` | +1.6 MiB |

  The header check before the decode reads the stored original in order through a 64 KiB buffer, as Go's `image.DecodeConfig` reads its `io.Reader`: the segments and chunks before the size (JPEG APPn, PNG ancillary chunks with their CRC, WebP RIFF chunks) are skipped piece by piece, never held whole. Only an original that passes is read for the decode: a JPEG, PNG or WebP whole (the decoder needs all of it), a GIF only up to the end of its first frame's image data, closed with a trailer, since image/gif's `Decode` returns the first frame. In `test/files/file-api.test.ts`, an uncached `?thumb=111x222` on a valid 256-frame 512×512 GIF of about 48 MB grows the peak RSS by about 20 MB, as much as a one-frame original; reading it whole (round 2 of the review) added 68.5 MB. The differential suite runs the same two cases against upstream: the over-limit PNG serves the original on both, and the multipart response has the same status, headers (`Content-Length` included) and body on both, with `HEAD` equal to `GET`.
- **Time:** iglo.base's 50 MP thumbs are faster (182 ms against 647 ms at one in flight) because of the pre-reduction; the 160 MiB download takes 188 ms against 144 ms.
