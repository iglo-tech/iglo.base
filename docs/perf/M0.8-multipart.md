# M0.8 spike: multipart record create near the 32 MiB body limit

Is iglo.base's memory per multipart request bounded, and does the body limit trip before the whole body is read? Measured against upstream on the same host.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, about 8 GiB available during the runs) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`) |
| Commit | `task/M0.8-spikes`, with `9a864c3` (below) |

## Method

`nice -n 10 bun scripts/spikes/M0.8/multipart.ts`. One pb_data, built through upstream's API, has two collections with create rule `""`:

- `notes`: a text field. Body limit 32 MiB.
- `uploads`: a text field and a file field with `maxSize` 32 MiB and `maxSelect` 1. Body limit 32 + 32 MiB.
- `bigfiles`: the same, with `maxSize` 256 MiB, for the 160 MiB case.

Each case runs on a fresh server process for each server and concurrency, on its own copy of that pb_data. The server gets one small warm-up create first. Then the case's requests go over raw sockets: 3 sequential requests at 1 in flight, and 2 rounds of 8 at 8 in flight. The 96 MiB cases use 2 and 1; the 160 MiB case runs once at 1 in flight only. The client writes the body in 64 KiB slices, waits for the socket to drain, and stops writing once the response starts.

What the columns mean:

- **Peak RSS**: the server's `VmHWM` after the run. A 20 ms `VmRSS` sampler agreed within a few MiB.
- **Peak − before**: the peak minus the server's RSS after the warm-up.
- **Body sent when the response began**: how much of the body the client had written when the first response byte arrived. Socket buffers add a few MiB on top of what the server actually read.

`TMPDIR` points to a directory on disk inside the spike root, which is deleted afterwards. On this host `/tmp` is a tmpfs, so files spilled there would count as memory, not disk.

iglo.base still refuses new uploads before M3.2: the `uploads` creates answer 400 "Failed to create record." after the body is parsed and the record is validated. Upstream stores the file and answers 200. So iglo.base's numbers cover parsing and validation, and upstream's also include writing the file.

For every case, both servers returned the same status and error body, apart from the M3.2 refusal.

- **`Content-Length` over the limit:** both servers answer 413 from the header alone. Neither reads the body or uses memory for it.
- **Chunked over the limit:** both read up to the limit and answer 413. With a 96 MiB body the client had written about 39 MiB when the response began: 32 MiB read by the server, plus socket buffers. The limit trips before the whole body is read.
- **Within the limit:** memory per request is bounded by the body limit on both servers. Each request holds a few copies of what it has read so far, and nothing outlives the request. One file part costs iglo.base about 2.5 times the file size at its peak: about 200 MiB for 31.9 MiB and 393 MiB for 160 MiB. Upstream stays at about 95 MiB whatever the file size: Go's `ReadForm` keeps at most 16 MiB of file data in memory and writes the rest to a temporary file, while iglo.base keeps every file part in memory (`src/server/multipart.ts`, as its header says).
- **Many small values:** iglo.base uses about 1.6 times upstream's memory.
- **Time:** at 1 in flight the two are close. At 8 in flight iglo.base takes about 1 s per request against 0.25–0.45 s, because it parses on one event loop (see M3.1's notes on multipart parsing and on concurrency).

## Defect found and fixed: Bun's 128 MiB request cap (`9a864c3`)

`Bun.serve` has a default `maxRequestBodySize` of 128 MiB. Without that setting, iglo.base closed the connection with no response for any request whose `Content-Length` was over 128 MiB. Upstream has no server-wide cap. It answers 413 from the body limit middleware, or accepts the upload when file fields raise the collection's limit (32 MiB + Σ `maxSize` × `maxSelect`, so a 160 MiB upload to `bigfiles` gets 200). The fix is one line in `src/server/serve.ts`: `maxRequestBodySize: Number.MAX_SAFE_INTEGER`, which leaves the decision to the body limit middleware. The fix is in its own commit with a differential test, `test/differential/request-body-size.test.ts`. It sends a `Content-Length` of 32 MiB + 1, 200 MiB and 4 GiB without a body. Upstream and iglo.base now both answer the same 413, and without the fix the two larger cases get no response.

## Answer

Memory per request is bounded by the body limit. No request buffers without bound, and nothing outlives the request. The limit trips before the whole body is read: from `Content-Length` before any body byte, and for chunked bodies at the limit. The one real difference was Bun's 128 MiB server cap, which dropped large uploads that upstream accepts; it is fixed in `9a864c3`.

What remains is the size of the bound. iglo.base keeps whole file parts in memory, at about 2.5 times the file size at peak. Upstream keeps at most 16 MiB per request in memory and writes the rest to a temporary file. A collection whose file fields allow large files is where this matters: with 256 MiB `maxSize`, 8 concurrent 250 MiB uploads would peak near 5 GiB in iglo.base and stay near 1 GiB in upstream.

**Proposal for M3.2 (lead decides):** port Go's spill in `ReadForm`. File part bytes beyond `maxFileMemoryBytes` (16 MiB) go to a temporary file, as `os.CreateTemp("", "multipart-")` does. The `File` handed to the record is then backed by that file (`Bun.file`), and the temporary files are removed when the request ends (Go's `Form.RemoveAll`). The record upsert and the M3.2 blob store then copy from disk instead of from memory. This brings iglo.base's peak to upstream's level whatever the file size. Measure it again with this script.

Note for deployment docs: both servers spill request bodies and multipart files to `TMPDIR`, which is `/tmp` by default. On hosts where `/tmp` is a tmpfs, as on this one, those files use RAM.
