# M0.6 read path spike (D8)

Decides how `src/db` runs reads and how it enforces `--queryTimeout`. Compared with [M0.4](M0.4-db-layer.md) where the same operation is measured. The decision is in [D8](../design/10-decisions.md#d8-sqlite-access-main-thread-connection-read-worker-pool-for-timed-reads).

## What upstream's timeout covers

Read from v0.41.0's source and checked against its binary:

- `--queryTimeout` (seconds, default 30, `pocketbase.go`) becomes `BaseAppConfig.QueryTimeout`; 0 or less means `DefaultQueryTimeout` (30 s, `core/base.go`).
- It is applied in exactly two places, both through `execLockRetry(app.config.QueryTimeout, defaultMaxLockRetries)` in a build hook:
  - `ModelQuery` and `AuxModelQuery` (`core/db.go`);
  - `RecordQuery` (`core/record_query.go`).
  
  These are the SELECTs behind record lists, views, counts, expands, rule checks, `Find*` helpers and the logs API.
- `execLockRetry` (`core/db_retry.go`) gives the query a `context.WithTimeout` if it has no context yet. The deadline covers all lock-retry attempts and the reading of the rows (`One`, `All`, `Row`, `Column`), and is removed afterwards.
- Raw `DB().NewQuery`, `DB().Select`, all writes and the `ConcurrentDB()` builders themselves get no timeout. The Go SQLite driver interrupts a query whose context ends (`sqlite3_interrupt`).
- Measured on the upstream binary with `--queryTimeout=1`, a superuser and 20,000 generated records: a records list with a cross-collection `?~` filter (an unindexed self join) answered after 1.02 s with `400 {"data":{},"message":"Something went wrong while processing your request.","status":400}`. Both the list and its count query logged `[1001.00ms]`, and the dev log showed `context deadline exceeded; failed query: SELECT DISTINCT ...` with the raw dbx SQL. A `/api/health` request sent during the query answered in 17 ms.

## What bun:sqlite can do

- **No interrupt.** Bun 1.4.4's `Database` has no `interrupt()` and no progress handler. Its methods are `run`, `query`, `prepare`, `exec`, `transaction`, `function`, `aggregate`, `onInsert`/`onUpdate`/`onDelete`, `serialize`, `fileControl`, `loadExtension`, `close`. The bun binary exports no `sqlite3_*` symbols (`nm -D`), so `bun:ffi` cannot call `sqlite3_interrupt` on Bun's SQLite.
- **`Worker.terminate()` does not stop a running statement.** A worker ran a cross join (20,000 × 20,000 rows) and was terminated after 1 s. `terminate()` returned in 0.3 ms, but the process kept using one full core for at least 10 more seconds (`/proc/self/stat`). Its `close` event fires only when the thread exits, after the statement step returns. A terminated worker that is between statements exits in about 4 ms.
- **Structured clone keeps rows intact** across `postMessage`: own `__proto__` keys, bigints above 2^53 and `Uint8Array` blobs.
- **`bun build --compile` needs the worker as an entry point.** `new Worker(new URL(...))` fails in the executable unless the worker file is a second entry point. Its path is then relative to the bundle's root. The `build` script now lists `src/db/read-worker.ts`. An executable built that way ran a pooled query.

## Method

Generated data: `bun test/perf/read-path/gen.ts .upstream/m06/big` writes a pb_data whose `data.db` has a records-like `posts` table with 1,000,000 rows (416 MB). It has a 15-character text id, indexed `created`, `status` and `author`, unindexed `title`, `score` and `body` (about 200 characters), and `ANALYZE` statistics. It is deterministic and takes 12 s. The M0.4 fixture is upstream's `tests/data` (`.upstream/pocketbase/tests/data`). Each run copies a dataset into `.upstream/m06/scratch` and deletes the copy afterwards.

Every query goes through `src/db`: `concurrentDB().newQuery(sql).bind(params)`, with `.all()` on the main-thread connection (**main**) or `.allAsync()` on the read pool with N workers (**pool N**, N = 2, 4 and 6, the CPU count).

| Workload | Fixture | 1M rows |
|---|---|---|
| lookup | `_collections` by random id | `posts` by random id (primary key) |
| page (30 rows, filter and sort) | `_migrations WHERE applied > 0 ORDER BY file DESC LIMIT 30` | `posts WHERE author = ? AND score > 50 ORDER BY created DESC LIMIT 30` (author indexed, about 1,000 rows each) |
| count | `COUNT(*) FROM _migrations` | `COUNT(*) FROM posts` |
| slow (unindexed filter) | `_collections WHERE fields LIKE '%needle-xyz%' ORDER BY created DESC LIMIT 30` | `posts WHERE body LIKE '%needle-xyz%' ORDER BY created DESC LIMIT 30` (full scan, no match) |

- **Alone** (`bun test/perf/read-path/bench.ts`): in one process.
  - Latency is measured one query at a time, for 2 s per workload (3 s for slow).
  - Throughput is measured with 8 queries outstanding, for the same time.
  - Event-loop lag: during the throughput phase, the lateness of a 5 ms interval timer.
  - Hop: `SELECT 1` latency for 1 s. The pool's cost per query is its value minus main's.
  - RSS: after warming every worker's connections.
- **Under HTTP load** (`bun test/perf/read-path/http.ts`): a server process (`Bun.serve`) runs one workload query per request; a client process keeps 8 requests outstanding for 3 s (6 s for slow). Meanwhile it sends a trivial `/health` request every 10 ms, one at a time. The server's `VmRSS` is read after warming.
- Everything ran under `nice -n 10`, one run at a time. The harness stops if RSS passes 2 GiB or MemAvailable falls under 2 GiB. The largest process was 333 MiB, and MemAvailable stayed above 11 GiB. One run of each.

The hop is the `SELECT 1` p50 of a pool minus main's: 0.06–0.11 ms. Memory per worker: about 7–12 MiB idle with the small fixture (server RSS 30 → 55 MiB for 6 workers), and about 40 MiB with warm page caches on the 1M-row database (server RSS 71 → 149/230/311 MiB for 2/4/6 workers). Each connection's page cache is bounded by `cache_size(-32000)`, 32 MB.

The "slow, alone" rows have few samples (5 queries in 3 s); their p95/p99 equal the maximum.

## Reading the numbers

- **Small queries.** On the main thread a lookup by id costs 0.011 ms, about the same as M0.4's 100,000 lookups/s. Through a worker it costs 0.13–0.18 ms, which is the hop. Under HTTP load the hop disappears in the request cost: main serves 21,556 lookups/s on 1M rows, pool 4 20,650, and both have a request p50 of 0.31–0.35 ms.
- **Slow queries stall the main thread.** With main-thread reads and 8 slow requests outstanding, a `/health` request waited 4.8 s (p50) behind the queued 610 ms scans. Even the 2.8 ms page query pushed `/health` to 28 ms p50 and 59 ms p99. With the pool, `/health` stayed at 0.3–0.4 ms p50 and under 8 ms p99 in every 1M-row cell, and the in-process event-loop lag stayed under 4 ms.
- **The pool adds throughput for slow queries.** Slow queries run in parallel on a pool: 1M-row page 330 req/s (main) → 586/1,025/1,188 req/s (2/4/6 workers), slow scan 1.6 → 3.2/6.2/8.5 req/s. From 4 to 6 workers adds 16–37 % on a 6-core host shared with the HTTP server, for another 80 MiB.
- **Pool size: 4.** It doubles the slow-query throughput of 2 and keeps memory near 230 MiB on a large database. 6 gives little more on this host. Upstream's 120 connections are not a goal: SQLite reads are CPU-bound here and the queue gives the same waiting behavior.

## The timeout

`test/db/read-pool.test.ts` checks the chosen design through the db API and a `Bun.serve` server. A ModelQuery with a 250 ms timeout runs a statement of about one second. The request answers at the deadline (240–450 ms), with ``context deadline exceeded; failed query: SELECT {{demo}}.* FROM `demo` WHERE ...``, upstream's text. Meanwhile a `/health` request and another pooled query are answered, the pool has replaced the worker, and one abandoned thread is still running. Two more checks: a query that waits in the queue past its deadline fails without stopping the running one, and a synchronous read that ends past the deadline (injected clock) fails with the same error.

What it costs: a timed-out statement keeps one core until it returns. The pool lets at most `size` such threads run at once; beyond that, replacements wait for one to exit, and queued queries fail at their deadlines. With upstream's default of 30 s, a statement must already take more than 30 s to get there.

## Compared with M0.4

Same machine and Bun. M0.4's single-row select by id outside a transaction ran at 75,000–110,000 ops/s on the main thread. This spike's main-thread lookup on 1M rows ran at 68,000 q/s with the event-loop yield of the harness, and stays the synchronous path. The async resolvers on the pool are new; there is no M0.4 equivalent.
