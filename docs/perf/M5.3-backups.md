# M5.3 backups: measurements

Run on 2026-10-31 on the shared host (6 cores, other work running), with Bun 1.4.4 and upstream v0.41.0, on a work directory on disk. Script: `test/perf/backups/run.ts`.

## 1 GiB pb_data

The fixture, plus a table of 500 MiB of base64 text in `data.db` and 500 MiB of storage files (2,500 files of 200 KiB, half random, half text, each with a sidecar). Each server ran on its own copy. RSS is sampled every 20 ms. Download and upload use curl. The restore time runs from the request until a marker record is gone after the restart, less upstream's 1 second wait.

| | iglo.base | upstream |
|---|---:|---:|
| Backup time | 16.2 s | 10.1 s |
| Zip size | 637 MiB | 652 MiB |
| RSS before the backup | 97 MiB | 37 MiB |
| Peak RSS, backup | 142 MiB | 220 MiB |
| Download time, peak RSS | 0.8 s, 112 MiB | 0.7 s, 62 MiB |
| Upload time, peak RSS | 5.2 s, 109 MiB | 3.7 s, 62 MiB |
| Restore time | 8.1 s | 7.5 s |
| Peak RSS, restore | 165 MiB | 189 MiB |

Request latency: `GET /api/collections/demo1/records?perPage=1`, one after the other with 5 ms between them.

| | requests | p50 | p99 | max |
|---|---:|---:|---:|---:|
| iglo.base, idle | 121 | 2.6 ms | 9.2 ms | 18 ms |
| iglo.base, during the backup | 2,060 | 1.9 ms | 12.2 ms | 30.9 ms |
| upstream, idle | 127 | 1.6 ms | 16.1 ms | 18.3 ms |
| upstream, during the backup | 1,342 | 1.6 ms | 12.2 ms | 29.5 ms |

- The server stays responsive: the VACUUM INTO copies, the compression and the extract run in the backup worker, and the main thread only walks `pb_data` and copies the finished zip in 1 MiB blocks with the event loop given back between them.
- Memory stays bounded: a backup adds about 45 MiB to the idle process, against 183 MiB upstream. Download, upload and restore stream too.
- The backup is 1.6× upstream's time. Almost all of the difference is Deflate: `node:zlib` gives about 110 MiB/s on base64 and random bytes in one thread.
- An earlier run stalled requests for up to 145 ms: the unlink of the large temp files was synchronous. They are removed asynchronously now.

### Deflate at the fastest level

`node:zlib` level 1 (Bun's zlib) uses fixed codes: on 1 MiB blocks of the test data it gives a ratio of 0.998 on base64 and 1.055 on random bytes (79 MiB/s), and the first zip was 760 MiB. Level 2 gives 0.753 at 44 MiB/s. `Z_HUFFMAN_ONLY` gives 0.753 and 1.000 at 111–126 MiB/s, but 0.555 on text, where level 1 gives 0.013 at about 3.4 GiB/s. So the writer compresses the first 64 KiB of each block at level 1, and a sample that stays above 90 % of its size sends the block to `Z_HUFFMAN_ONLY`. Each block is compressed on its own with a sync flush, which keeps the Deflate stream valid and the memory bounded.

`Bun.deflateSync` with libdeflate is about as fast, but it can only end a stream, so it cannot do a large file in bounded memory.

VACUUM INTO of the 500 MiB database takes 2.3 s; connection pragmas change nothing (`cache_size`, `temp_store` and `synchronous=NORMAL`: 2.1–2.3 s).

## Above 4 GiB, by hand

`pb_data` was the fixture plus `storage/big/a-zero.bin` (sparse, 4.3 GiB of zeros) and `storage/big/b-random.bin` (4.3 GiB of random bytes). The files were deleted afterwards.

| Direction | Backup | Zip | End record | Restore |
|---|---:|---:|---|---|
| iglo.base made it, upstream restored it | 79 s | 4.36 GiB | records, size and offset all at the Zip64 markers | through the API; SHA-256 of `b-random.bin` equal, size of `a-zero.bin` equal |
| upstream made it, iglo.base restored it | 47 s | 4.32 GiB | offset at the Zip64 marker | through the API; SHA-256 of `b-random.bin` equal, size of `a-zero.bin` equal |

Upstream's restore is Go's `archive/zip`, so Go reads the Zip64 archives iglo.base writes. Both the entries over 4 GiB and the offsets past 4 GiB were covered. The zip was hard-linked into the other server's backups directory for this run, as the upload goes through the same reader.

Zip64 above 65,535 entries: a test in `test/tools/archive/archive.test.ts` writes 65,536 entries and reads them back; iglo.base writes the Zip64 end records then, as Go does.
