# M4.8: rate limiter

The rate limit check runs on every request, and the records handlers call it once more. With rate limiting disabled it reads one boolean (`rateLimits.enabled`) on the global middleware or on `checkCollectionRateLimit`, before any label is built. The question: does that show on the records list?

## Setup

| | |
|---|---|
| Date | 2026-10-31 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; 9 GiB available during the runs) |
| Bun | 1.4.4 |
| Commits | before `2bc7500` (`main`), after `task/M4.8-rate-limiter` |

`nice -n 10 bun test/perf/records-read/bench.ts --requests 8000 --keep <dir>`: 8,000 requests per workload after 300 warm-up requests, 8 in flight, as a guest, over keep-alive connections, on one kept copy of the data (10 teams, 50 members, 200 posts). Rate limiting is off, as in the data's default settings. The two builds ran alternately, two runs each, one measurement at a time. Other work may have run on the host, so differences within a run's noise mean nothing.

## Results

Requests per second, with p50 / p99 in ms.

| Workload | Before, run 1 | After, run 1 | Before, run 2 | After, run 2 |
|---|---|---|---|---|
| list 30 | 1,076 (6.25 / 20.21) | 1,179 (5.85 / 17.09) | 1,123 (5.68 / 19.48) | 1,104 (6.10 / 19.27) |
| list 30, relation rule | 1,017 (6.54 / 20.80) | 1,081 (6.40 / 17.69) | 1,028 (6.37 / 20.45) | 1,081 (6.19 / 20.67) |
| list 30, expand author.team | 390 (18.70 / 47.92) | 389 (18.64 / 48.90) | 392 (18.15 / 50.88) | 355 (19.99 / 56.33) |
| view | 5,712 (1.17 / 4.91) | 5,724 (1.19 / 4.43) | 5,864 (1.18 / 4.16) | 5,935 (1.14 / 4.24) |

The differences go both ways and stay inside the spread between runs of one build, so the disabled check has no measurable cost. The one lower number, the expand workload in run 2, is not repeated in run 1 and upstream's own rate moved by 19% between the same two runs.
