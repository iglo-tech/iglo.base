# M1.8a: exact-integer reads (`withExactIntegers`)

Council round 1 of M1.8a found that a record row read with the default integer narrowing cannot tell an INTEGER from a whole REAL value, so `nullStringMapFromRow` formatted INTEGER values from 1e6 on as floats (`1.234567e+06`). `Query.withExactIntegers()` (`src/db/dbx/query.ts`, `src/db/dbx/rows.ts`, the read pool and worker) reads rows without narrowing: every INTEGER value stays a `bigint`, so a `number` is always a REAL. It is opt-in; other callers keep the narrowed values. The default path gains one boolean check per row.

## Setup

Same machine and method as `docs/perf/M0.4-db-layer.md`: AMD Ryzen 5 1600, 16 GiB RAM, Linux 6.12 VM, Bun 1.4.4, `nice -n 10 bun test/db/bench.ts --dir .upstream/bench`, measured on 2026-10-28. "Before" is the PR head before the change (`5a447a3`), "after" is this change, in alternating runs; three runs each, ranges shown. The bench gained one measurement, the 10,000-row select read `withExactIntegers`.

## Results

| Measurement | Before (`5a447a3`) | After |
|---|---|---|
| Open `data.db` + `auxiliary.db` (median of 20) | 0.77–0.91 ms | 0.81–0.92 ms |
| Single-row insert, outside a transaction | 22,299–27,703 ops/s | 21,469–25,720 ops/s |
| Single-row insert, inside one transaction | 121,040–181,026 ops/s | 141,372–166,157 ops/s |
| Single-row select by id, outside a transaction | 95,614–105,344 ops/s | 91,884–105,321 ops/s |
| Single-row select by id, inside one transaction | 128,754–158,607 ops/s | 105,813–149,758 ops/s |
| 10,000-row select (median of 20) | 3.25–3.73 ms | 3.05–3.25 ms |
| 10,000-row select `withExactIntegers` (median of 20) | — | 2.64–2.85 ms |

The default path is unchanged within the run-to-run variation. Reading `withExactIntegers` skips the narrowing and is about 0.4 ms faster on 10,000 rows of three columns.
