# M0.8 spike: bcrypt round trip between iglo.base and upstream

Does a password hash written by one server verify on the other, at cost 10 and 12, through the HTTP API? The edge cases are the 72-byte bcrypt limit and non-ASCII passwords.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, about 8 GiB available) |
| Bun | 1.4.4 (`Bun.password`, bcrypt) |
| Upstream | PocketBase v0.41.0 release binary (golang.org/x/crypto bcrypt) |
| Commit | `task/M0.8-spikes` |

## Method

`nice -n 10 bun scripts/spikes/M0.8/bcrypt.ts`. Only one server runs at a time, and both use the same pb_data. Upstream creates two auth collections: `u10` and `u12`, with a password field of cost 10 and 12 (min 8), and create and update rule `""`. The steps:

1. **Upstream:** creates one user per password case in both collections, through `POST /records`, and signs each one in.
2. **iglo.base:** signs in upstream's users. It creates the same cases as its own users, and changes the password of upstream's users through `PATCH /records/:id` as superuser. The new password is the same, so the change writes a new salt and hash. Then it signs those users in again.
3. **Upstream:** signs in iglo.base's users and the users that iglo.base changed, then changes the password of iglo.base's users.
4. **iglo.base:** signs in those.

Every sign-in is also tried with variants of the password: wrong, shorter, longer, and other Unicode forms. Each sign-in that ran on both servers is compared by status and error body.

Between the steps the spike reads the stored hashes from `data.db`. It also writes raw hashes into two users: a Bun.password `$2b$` hash, and the same hash with a `$2y$` prefix. Both servers then sign those users in.

Last, sign-in time on each server. The same user signs in 10 times one after another, after 2 warm-ups. Then 8 sign-ins go at once, in 3 rounds, while `/api/health` is requested over and over.

Password cases (bytes in UTF-8):

| Case | Password | Bytes | Variants tried at sign-in |
|---|---|---|---|
| ascii | `1234567890` | 10 | last character changed; one character shorter |
| ascii-71 | 71 ASCII characters | 71 | +1 byte (72); +3 bytes (74) |
| polish | `zażółć gęślą jaźń` (NFC) | 26 | NFD form; ASCII-folded |
| emoji | `🔑🔒🗝️ klucz 鍵` | 25 | without the U+FE0F variation selector |
| z36 | `ż` × 36 | 72 | +1 byte (73); +`ż` (74); 35 × `ż` + `a` (71) |
| emoji-72 | `🔑` × 18 | 72 | + another emoji (76); last emoji changed (72) |
| emoji-straddle | `🔑` × 17 + `abc` | 71 | + an emoji whose first byte is byte 72 (75) |
| z40 | `ż` × 40 (40 characters, under the 71-character limit) | 80 | none |

## Results

- **Results:** 158 checks ran on both servers: creates, updates, and sign-ins with the right password and every variant. Both servers gave the same status and body in all 158. Every variant gave the expected result.
- **Stored format:** iglo.base stores `$2a$<cost>$…`, as upstream does. `Bun.password` writes `$2b$`, and `src/tools/crypto/bcrypt.ts` rewrites the prefix; the computation is the same for passwords of at most 72 bytes. The cost is the field's. All 14 updates on each side wrote a new hash, and the other server verified it.
- **Other prefixes:** a raw `$2b$` hash from `Bun.password` and a `$2y$` hash both sign in on both servers (200).
- **The 72-byte limit:** both servers refuse to create a password longer than 72 bytes with 400 "Failed to create record.". The z40 case shows it: 40 characters pass the field's 71-character check, but 80 bytes fail Go's `ErrPasswordTooLong`, and iglo.base fails the same way. At sign-in both compare only the first 72 bytes. A longer input whose first 72 bytes match signs in (z36 +1 byte, z36 +`ż`, emoji-72 + another emoji). A 71-byte password does not match an input with any 72nd byte (ascii-71 +1 and +3), because bcrypt's terminating NUL takes that place. An emoji split at byte 72 counts only by its first byte (emoji-straddle).
- **Non-ASCII:** both servers compare bytes, without Unicode normalization. NFD does not match NFC, and leaving out the variation selector does not match.

## Answer

The results do not differ, so no fix is needed for correctness. Hashes written by iglo.base verify on upstream and the other way round, at cost 10 and 12, through create, update and sign-in. The 72-byte limit and non-ASCII passwords behave the same on both, and so do raw `$2b$` and `$2y$` hashes.

The spike also found a performance difference. iglo.base hashes and verifies with `Bun.password.hashSync` and `verifySync` on the event loop (`src/tools/crypto/bcrypt.ts`, called from `src/fields/password.ts`). One sign-in takes as long as upstream's, but concurrent sign-ins run one after another, and every other request waits behind them. With 8 sign-ins at once at cost 12, iglo.base takes 1.9 s against upstream's 0.42 s, and `/api/health` waits 1.9 s against 15 ms. A handful of sign-in attempts can stall the whole server for seconds.

**Proposal (lead decides; M4.1 code, or M7):** run bcrypt off the event loop.

- **Sign-in:** use the async `Bun.password.verify` on the canonical `$2b$` form. It runs on Bun's thread pool. The Go-computation fallback, for salts outside the alphabet, can stay synchronous.
- **Hashing:** the `PasswordField` setter hashes when the value is set, which is synchronous like upstream's. It could hash with `Bun.password.hash` before the save instead. Another option is moving both into the existing read worker pool.

Measure again with this script; the results table must stay identical.
