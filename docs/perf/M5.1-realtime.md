# M5.1: realtime with 1,000 connections against upstream

Does `/api/realtime` hold 1,000 subscribed connections and fan record changes out to them as well as upstream v0.41.0 does, with bounded memory? Measured through HTTP on both servers, one server at a time.

## Setup

| | |
|---|---|
| Date | 2026-10-30 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, 8.3–8.8 GiB available during the runs, never under 8.2 GiB) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`) |
| iglo.base | `dist/iglo-base` from `bun run build`, branch `task/M5.1-realtime`, 4 read workers (the `serve` default) |
| Command | `nice -n 10 bun test/perf/realtime/measure.ts` (after `bun run upstream:prepare` and `bun run build`) |

## Method

Each server runs on its own fresh pb_data: a superuser created with upstream's `superuser upsert`, a user, and two collections with a 100,000-character text field: `notes` (list and view rule `""`, no query needed) and `private` (rule `@request.auth.id != ''`, one SQL query per check on upstream). The clients are raw sockets in the measuring process, which parses every stream, so the client side costs the same for both servers.

1. Open 1,000 connections, 50 at a time, each waiting for `PB_CONNECT`, and subscribe each as a guest to `notes/*`. RSS and open file descriptors come from `/proc/<pid>`.
2. 20 broadcasts with 64 B of data and 5 with 16 KiB: a record create in `notes` through the records API, 200 ms apart. Latency runs from just before the create request is sent to each client's receipt of the event.
3. Every client subscribes to `private/*` with the user's token (1,000 separate requests, so 1,000 separate auth record instances), then 20 64 B creates in `private`.

The script stops a server when MemAvailable falls under 1.5 GiB (it never did) and removes its data.

Measured on the review fix, both servers again, the same day and machine (8.3–8.5 GiB available); the first run's iglo.base numbers are in the before/after tables below.

The RSS before is higher on iglo.base because of the whole app, not realtime: the read workers, the embedded dashboard and the runtime (the M0.8 spike server without them started at 22 MiB).

- **Connections:** a subscribed connection costs iglo.base a fifth of upstream's memory and the same one descriptor.
- **Rule checks:** upstream checks the rule once per subscriber and message, and so did the first iglo.base implementation. Within one broadcast iglo.base now shares one check between the subscribers whose check reads the same values: the record, the rule, the subscription's query and headers, and the auth record as the field resolver sees it (its collection and unhidden export, memoized per auth record instance). The result cannot differ, since those are all the check reads. With every client authenticated as the same user, 1,000 checks become one query; with 1,000 different users the cost is one export per auth record, done once while the client holds that record. Each subscriber's message is still encoded once per distinct visibility (superuser, email visible, `fields`), not once per client.
- **Response time:** as upstream, the create request is answered only after its broadcast is prepared: every subscriber's rule check, subscription filter, email visibility check and expand, read synchronously on the main-thread connection right after the commit, so they see the state that write left and no later one (an earlier version answered first and checked later against the live database, which could show a guest a private draft that the next write published). Only the sending to the streams follows the response. iglo.base answers in 12–20 ms with 1,000 subscribers, upstream in 16–61 ms. The cost is that a slow rule or expand query of a broadcast blocks the event loop as any synchronous read does (D8); the shared checks below keep it to one query per distinct check.
- **64 B broadcasts with a `""` rule** reach the clients later than upstream's (p50 23 ms against 14 ms; p99 46 against 33 ms). The broadcast itself takes about 1.4 ms in-process for 1,000 clients. The rest is the time `Bun.serve` takes to move 1,000 `ReadableStream` bodies to their sockets after the create response. One combined chunk per message instead of the three upstream writes (head, shared data, end) did not change the 64 B time and made 16 KiB slower (p50 62 ms), so messages keep the shared data buffer. With 16 KiB messages iglo.base is faster than upstream.

### Before and after (iglo.base)

The same command on the first implementation (one rule check and one record copy per subscriber, the data encoded per visibility):

| 64 B, `@request.auth.id != ''`, 1,000 subscribers | first implementation | shared checks |
|---|---|---|
| per client p50 / p99 | 85.8 / 156.7 ms | 26.3 / 48.4 ms |
| last client p50 / max | 144.1 / 166.4 ms | 43.0 / 53.7 ms |

The `""`-rule numbers did not change (24 ms p50 for 64 B, 40–43 ms for 16 KiB).

The review fix (the checks read synchronously right after the commit, before the response, instead of on the read pool after it):

| 1,000 subscribers | checks after the response | checks before the response |
|---|---|---|
| create response p50: 64 B, 16 KiB, rule | 4.9, 7.3, 4.9 ms | 12.4, 19.7, 16.5 ms |
| 64 B, `""` rule: per client p50 / p99 | 24.4 / 47.6 ms | 22.9 / 45.7 ms |
| 16 KiB, `""` rule: per client p50 / p99 | 42.7 / 68.8 ms | 39.2 / 71.4 ms |
| 64 B, `@request.auth.id != ''`: per client p50 / p99 | 26.3 / 48.4 ms | 25.9 / 50.3 ms |

Delivery did not change; the response now includes preparing the 1,000 messages and is still faster than upstream's.

## Limits

- **Idle and maximum time:** 5 minutes without a delivered message and 30 minutes in all, as upstream. Bun's server idle timeout is turned off on the realtime request only (`server.timeout(req, 0)`); other requests keep Bun's 10 s default. Tested with injected timers and a 1 s server idle timeout in `test/realtime/connection.test.ts`.
- **A client that stops reading** is closed once more than 8 MiB are unsent (D27, a deliberate difference in [API compatibility](../design/04-api-compatibility.md#deliberate-differences)); upstream holds everything for it. The bound counts the stream's queue above a 64 KiB high water mark, so a stuck client costs at most about 8 MiB plus the kernel socket buffers. Tested in `test/realtime/connection.test.ts`.
- **Shutdown:** SIGTERM closes every realtime stream before the server stops, so the server exits at once instead of waiting out upstream's 1 s limit (`test/realtime/shutdown.test.ts`).
