# M1.8c record save and delete

First implementation of the record save, validate and delete chain (`src/records/record-save.ts`) and `truncateCollection`, so there is no "before". The numbers put iglo.base's entry points next to upstream PocketBase v0.41.0's records API for the same work; later changes to this path compare against them, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-28 |

| Commit | `task/M1.8c-record-save` |

## Method

`nice -n 10 bun test/records/bench-save.ts` after `bun run upstream:prepare`, with the host otherwise idle. A fresh upstream install gets four base collections through `POST /api/collections`: `wide` (20 fields: id, 4 text, editor, 3 number, 2 bool, email, url, date, select, multi-select, json, geoPoint, created, updated), `cparents` and `cchildren` (a single relation to `cparents` with `cascadeDelete`) and `trunc` (one text field). Upstream's endpoints are timed first (HTTP round trips on 127.0.0.1 as a superuser, so request parsing, the form, the handler and the JSON response are included). Upstream then stops, and iglo.base's functions run in the bench process on a copy of the same `pb_data`: `newRecord` + `load` + `saveRecord` for a create, `findRecordById` + `load` + `saveRecord` for an update (upstream's update handler also loads the record), `findRecordById` + `deleteRecord` for the cascade, and `truncateCollection`. The 1 parent with 1,000 children and the 10,000 truncated rows are inserted with SQL before each run (`POST /api/sql` upstream, the same statement on iglo.base) and are not timed. Each figure is the median of the runs (200, 200, 5 and 3) after one warm-up run.

## Results

Two runs; the second in parentheses.

| Operation | iglo.base | upstream (HTTP) | upstream request |
|---|---|---|---|
| create, 20 fields | 0.61 ms (0.69 ms) | 1.77 ms (0.98 ms) | `POST /records` |
| update, 20 fields (5 changed) | 0.39 ms (0.49 ms) | 2.31 ms (1.23 ms) | `PATCH /records/{id}` |
| delete with a cascade over 1,000 records | 42.5 ms (42.5 ms) | 185.9 ms (114.1 ms) | `DELETE /records/{id}` |
| TruncateCollection, 10,000 records | 182.3 ms (193.7 ms) | 462.8 ms (357.5 ms) | `DELETE /collections/{c}/truncate` |

- The two sides do not do the same amount of work: upstream's figures include HTTP, the request form and the JSON response, and its writes go through its hook system. They show that the save chain itself is not the bottleneck; the records API task (M3.1) measures endpoint against endpoint.
- The cascade and the truncate do the same work per record on both sides: each related record is read again by id and deleted through the whole chain (interceptors, the delete, the auth-ref and cascade checks) in one transaction, about 40 µs (cascade) and 19 µs (truncate) per record on iglo.base.
