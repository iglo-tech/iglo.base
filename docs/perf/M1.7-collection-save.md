# M1.7 collection save: table sync and view creation

First implementation of the collection save path (`src/collections/collection-save.ts`, `collection-record-table-sync.ts`, `view.ts`), so there is no "before". The numbers compare iglo.base with upstream PocketBase v0.41.0 doing the same work; later changes to this path compare against them, measured the same way.

| | |
|---|---|

## Method

`nice -n 10 bun test/collections/bench-save.ts` after `bun run upstream:prepare`, with the host otherwise idle. Each scenario starts from its own fresh upstream install (`pocketbase superuser upsert`), copied for both sides.

- **iglo.base** runs in a child `bun` process that opens its copy with `Databases.open`, loads the collections cache and does what upstream's collections handler does (the collection from `newCollection` or `findCollectionByNameOrId` with the JSON body unmarshaled into it), then times `saveCollection` alone. Peak memory is `process.resourceUsage().maxRSS` of that process.
- **upstream** runs `pocketbase serve` on its copy and gets the same bodies through `POST`/`PATCH /api/collections` (rows through `POST /api/sql`). Times are the HTTP round trips on 127.0.0.1, so they include request parsing, the handler and the response. Peak memory is the server's `VmHWM` from `/proc/<pid>/status`.

Peak memory is shown after the scenario's setup and at its end, for the whole process (both runtimes' baseline included).

Scenarios:

- **50 fields:** create a base collection with 50 fields (text, number, bool, email, url, date, select, json, editor, file, five of each): validation, the `_collections` insert, `CREATE TABLE`, `PRAGMA optimize`. Median of 5 creates.
- **Single ↔ multiple, 100,000 rows:** a base collection `big` with a select field `tag` (`maxSelect: 1`) and 100,000 rows inserted by SQL; the field is changed to `maxSelect: 3` and back. Each change drops and restores the views, renames the column, adds the new one, copies the 100,000 values with upstream's `UPDATE … CASE … json_array(…)` / `json_extract(…, '$[#-1]')` and drops the old column. Median of 3 changes in each direction.
- **View resave:** a view `big_view` (`select id, tag, <n> as n from big`) over the same 100,000-row table, saved with a changed query: field generation (temporary views and `PRAGMA_TABLE_INFO`), the dry run with a 10-row sample, `normalizeViewQueryId`, `DROP VIEW` and `CREATE VIEW`. Median of 5 saves.

## Results

Two runs; the second in parentheses. Memory in MiB.

| Scenario | iglo.base time | upstream time | iglo.base peak (setup → end) | upstream peak (setup → end) |
|---|---|---|---|---|
| Create a base collection with 50 fields | 23.3 ms (16.5 ms) | 21.2 ms (19.8 ms) | 53 → 73 (52 → 72) | 35 → 37 (33 → 34) |
| Select single → multiple, 100,000 rows | 93.1 ms (88.6 ms) | 179.1 ms (204.5 ms) | 63 → 85 (63 → 82) | 43 → 54 (45 → 54) |
| Select multiple → single, 100,000 rows | 103.0 ms (101.6 ms) | 190.1 ms (204.2 ms) | (same run as above) | (same run as above) |
| View resave over 100,000 rows | 10.0 ms (18.2 ms) | 10.4 ms (16.4 ms) | 65 → 77 (64 → 76) | 45 → 46 (46 → 46) |

- The single ↔ multiple change is SQLite work (rename, add, a 100,000-row `UPDATE`, drop column). iglo.base takes about half of upstream's time; the difference is the SQLite build (Bun's native SQLite 3.53.4 against upstream's transpiled modernc.org/sqlite).
- Creating a collection and resaving a view take about the same time on both. iglo.base's times exclude HTTP, upstream's include it, so iglo.base's save itself is a little slower here; most of it is the validation and JSON work in JavaScript.
- iglo.base's process starts higher (Bun's runtime, about 50 MiB against Go's 33 MiB) and grows by 12–22 MiB during a scenario; upstream grows by 1–11 MiB. None of the scenarios holds rows in memory: the 100,000 values are copied inside SQLite, and the dry run reads 10 rows.
