# M5.4b S3 file storage: measurements

Run on 2026-11-01 on the shared host (6 cores, other work running), with Bun 1.4.4 and upstream v0.41.0, on a work directory on disk, against a local versitygw (posix backend, same disk). Script: `test/perf/files/s3.ts`. Each server ran on its own copy of the fixture and its own bucket.

## A 100 MiB file

A 100 MiB file of random bytes, four runs each, as ranges over the runs. Upload and download use curl. RSS is sampled every 20 ms. `GET /api/health` runs one request after the other with 5 ms between them, so a step gives 14 to 125 samples and its p99 is close to its maximum. "Intake" sends the same body to a field that refuses it by its MIME type: the multipart intake alone, with no S3 call.

| | iglo.base | upstream |
|---|---:|---:|
| Intake, time | 0.5–0.7 s | 0.3–0.4 s |
| Upload, time | 0.7–0.9 s | 0.6–0.9 s |
| Upload, peak RSS | 248–308 MiB | 131–165 MiB |
| Download, time | 0.4–0.5 s | 0.2–0.3 s |
| Download, peak RSS | 199–252 MiB | 98–143 MiB |

`GET /api/health` meanwhile:

| | p50 | p99 |
|---|---:|---:|
| iglo.base, intake | 29.7–40.4 ms | 47.4–82.1 ms |
| upstream, intake | 0.4–0.5 ms | 6.8–16.8 ms |
| iglo.base, upload | 1.4–2.5 ms | 48.9–93.8 ms |
| upstream, upload | 0.4–0.6 ms | 5.1–17.7 ms |
| iglo.base, download | 0.5–0.6 ms | 3–10.7 ms |
| upstream, download | 0.5–0.6 ms | 4.5–16.9 ms |

- The stalls during an upload come from the multipart intake, not from S3: the intake alone, which makes no S3 call, stalls as long, and its median is worse because the whole step is intake. That is the M3.2 path of the hardening backlog's M5.4a row ("Uploads"), which this task does not own, for M7.1.
- During a download the server stays as responsive as upstream. Every S3 call is an awaited `fetch`.
- Memory stays bounded: the upload reads the D27 spill a part at a time, at most five 6 MiB parts. RSS includes uncollected buffers.
- A download costs the file's size on disk until its response ends, as the bytes are spooled first ([API compatibility](../design/04-api-compatibility.md#deliberate-differences)). That is why it takes about twice upstream's time, and why the first byte comes last.
- A thumb spools its original to the temp directory as well, so an original over `PB_THUMBS_MAX_SOURCE_PIXELS` is downloaded before it is refused, where upstream reads only the header. It reaches disk, not memory, and the failure falls back to the original as upstream's does.
