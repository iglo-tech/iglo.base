# M3.2: file uploads, memory before and after the multipart spill (D27)

Does storing uploaded files keep iglo.base's memory per request bounded near upstream's? Measured with the M0.8 script on the same host, one case at a time.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, about 8 GiB available during the runs) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`) |
| Command | `nice -n 10 bun scripts/spikes/M0.8/multipart.ts --only file,file-160` |

The method, collections and columns are those of [M0.8](M0.8-multipart.md): a fresh server per case and concurrency, one warm-up create, then 3 sequential requests at 1 in flight and 2 rounds of 8 at 8 in flight (the 160 MiB case once at 1 in flight). `TMPDIR` points to a directory on disk inside the spike root, which is deleted afterwards. The script's MemAvailable guard (stop below 1.5 GiB) never tripped.

- **Before:** `task/M3.2-local-files` with the file storage (uploads are stored, 200) but without the spill: every file part is kept in memory, as `src/server/multipart.ts` did until then.
- **After:** the same branch with the spill: Go's `ReadForm` rule, file data past 16 MiB per request (`maxMemory`) goes to one temporary file per request (`os.CreateTemp("", "multipart-")`), the record gets a `File` that reads a section of it, and the file is removed when the request ends.

In M0.8 iglo.base still refused uploads (400), so its numbers there cover parsing and validation only; both rows below also write the file into `pb_data/storage` (temporary file, MD5, `.attrs`, rename), as upstream does.

## Results

| Case | Server | In flight | Status | RSS before (MiB) | Peak RSS (MiB) | Peak − before | ms p50 / max |
|---|---|---|---|---|---|---|---|
| one 31.9 MiB file part (`uploads`) | upstream | 1 | 200 | 33–35 | 130 | 95–97 | 196–215 / 220 |
| | upstream | 8 | 200 | 35–36 | 964–989 | 929–953 | 2,399–2,642 / 2,705 |
| | iglo.base before | 1 | 200 | 70 | 335 | 265 | 252 / 286 |
| | iglo.base after | 1 | 200 | 70 | 185 | 114 | 215 / 278 |
| | iglo.base before | 8 | 200 | 70 | 1,078 | 1,008 | 1,593 / 2,140 |
| | iglo.base after | 8 | 200 | 71 | 601 | 529 | 2,081 / 2,829 |
| one 160 MiB file part (`bigfiles`) | upstream | 1 | 200 | 33 | 129–131 | 95–97 | 866–1,063 |
| | iglo.base before | 1 | 200 | 71 | 623 | 552 | 1,248 |
| | iglo.base after | 1 | 200 | 71 | 155 | 84 | 1,335 |

Upstream's two rows per case are its runs in the before and the after measurement (ranges).

- **160 MiB upload:** the peak drops from +552 MiB (about 3.4 times the file) to +84 MiB, near upstream's +95–97 MiB and no longer a multiple of the file size. What remains is the request body copy (`RereadableReadCloser`, 16 MiB in memory then a temporary file, as upstream), the 16 MiB of the file part kept in memory before the spill, and the copy buffers.
- **31.9 MiB, 8 in flight:** +529 MiB against +1,008 MiB before, and below upstream's +929–953 MiB.
- **Time:** about the same at 1 in flight. Storing reads the file once more from the temporary file (and hashes it for `.attrs`); the 160 MiB case takes 1.3 s against upstream's 0.9–1.1 s.

## Answer

With the spill, iglo.base's peak memory for a large upload is near upstream's whatever the file size (D27's goal), and stored uploads keep it bounded. The spill writes to `TMPDIR` (`/tmp` by default), as Go does; on hosts where `/tmp` is a tmpfs those files use RAM (see the M0.8 note).
