# M7.1c: JSON writer, log export, per-request overhead, and the final numbers

Items 1, 3 and 4 of the [M7.1b report](M7.1b-fixes.md) "Ranked for M7.1c", then the final measurement against the [performance bar](../design/02-architecture.md#performance-bar). API output is unchanged: the new tests compare the new code with a copy of the M7.1b code over generated corpora, and `bun run check` and `bun run test:reference` pass.

## What changed

| # | Change | Where | Gain |
|---|---|---|---|
| 1 | **JSON writer.** `Record.marshalJSON` writes the members itself: no `Map` to object copy (`setOwn` = `defineProperty` per member), no entries array, no sort and no quote per record. The sorted member order and the pre-quoted names are computed once per field list (`recordJSONLayout`, checked against the field objects and names on every use, so a rename or hide cannot leave a stale layout; collections with a name that needs escaping or a field named `expand`, `collectionId`, `collectionName`, and records with custom data go through the generic path). Strings with nothing to escape are copied between quotes (one regex test); a marshaler's output (a `json` field, a date) that is already compact and canonical is checked in one pass without allocation (`isCanonicalCompactJSON`) and used as it is instead of parsed and rebuilt; nested records are trusted (`canonicalJSON`). `Object.entries` arrays are gone from the object path. | `src/tools/types/go-json.ts`, `src/records/record-json.ts` (new), `record-model.ts` | 30-record list with an expand level, JSON only: 1,100 µs to 170 µs |
| 2 | **Read-pool batching: removed after review.** An idle worker took up to 4 queued reads in one `postMessage` (pool micro-benchmark: `select 1` 46k to 90k reads/s). Once a read is posted in a batch the pool cannot stop it, so it waited behind unrelated slow statements, ran after it had failed at its deadline, and ran twice after a takeover, which breaks D8 (per-query deadline, FIFO queue, four live workers). A correct design needs cancel flags, a new takeover order and a D8 rewrite: more risk than the micro-benchmark gain justifies for the MVP. `read-pool.ts`, `read-worker.ts` and their tests are as on `main`. | none | none |
| 3 | **Log row export.** The generic object path above now also writes the request log attrs (`Object.keys` and a values array instead of entry pairs, fast quote). The byte counts of the message, the data and `cutStr` are skipped when `length * 3` is under the limit (a UTF-16 unit is at most 3 bytes). The log time is formatted from `toISOString` for years 1000 to 9999. No dedicated attrs builder was written: the generic path is within a microsecond of what one would give. | `go-json.ts`, `src/logs/log-model.ts`, `src/middlewares/activity-logger.ts` | `logDBExport` of a request log: 6.3 µs to 2.6 µs |
| 4 | **Per-request overhead.** `ValidationErrors` (so every `new Errors()` of the validation chain, one per field validated) and `JsonEOFError` (thrown on each incomplete prefix while a request body is read) no longer capture a stack trace: that was the `Error` native of the create profile (about 3% of it). The limit is restored with the message built first, so a throwing `errorText` cannot leave it at 0. | `src/server/error.ts`, `json-decode.ts` | about 3% of the create profile |

Item 4, change by change: the **stack-less errors are kept** (profile-visible). Three other changes of the first version of this PR had no measurable effect and are **removed**: the `cleanSlashPath` fast path (and its test), the `unmapIPv4` guard in `serve.ts` and the single-chunk `Uint8Array` response body (`router.ts`). For the last one the `/api/health` drop from 15,443 to 10,275 req/s at 8 clients was checked: the same executable with and without it, alternated, 3 repetitions each, gave 10,942 to 14,115 req/s with it and 10,211 to 13,501 without it. The cell varies by about 30% between repetitions on this shared host, so the drop was noise, and the change gave nothing either way.

**`logSQL` needed no change.** `queryLogFunc?.(ms, this.logSQL(), err)` does not evaluate its arguments when there is no function, and the function is set only in dev mode (`--dev`, or any run from source). The `logSQL` in the M7.1a and M7.1b profiles (2.5% of the expand profile) is an artifact of profiling `src/main.ts`, which is a dev run that also prints every log line. `bench.ts --cpu-prof` now passes `--dev=false`, so profiles match the compiled executable.

Left out: the expand driver (#6 of the M7.1b ranking) and `Object.entries` in `fieldsData` (#5): not asked in this brief's list and the new profile does not rank them first.

## Profiles

Microbenchmarks of one item each are above. The effect on the whole is the table: list and expand 1.3 to 1.6× the throughput of before, view 1.27×.

**What remains: create.** Profile of the source (`--dev=false`, 50 clients, 8 s): the SQLite insert (`run`, native) is 16.9% self, the request body stream natives (`onRSDefaultController*`) 4.8%, JSON body decoding (`json-decode.ts` `string`, `object`, `setOwn`) about 3.5%, the record save chain the rest; the `Error` native is gone. The insert and its commit run synchronously on the main thread (the write connection), while upstream commits on a Go thread beside its request threads, so upstream's create keeps scaling with cores (2,938 req/s at 50 clients against 1,775) while ours is one thread at 100% of one core with the other cores idle. That is single thread against many cores: moving writes to a thread is a different design (D8 keeps the writer on the main thread) and multi-process or multi-thread serving is ruled out by the owner. The p95 is within the bar (1.12).

**List and expand**: what is left in the profile of the first version is the read-pool hop (`postMessage`), hydration (`hydrateRecord`) and the `publicExport` of expand records, each a few percent; the profile was not retaken after batching was removed.
