# M7.1c: JSON writer, read-pool batching, log export, per-request overhead, and the final numbers

Items 1 to 4 of the [M7.1b report](M7.1b-fixes.md) "Ranked for M7.1c", then the final measurement against the [performance bar](../design/02-architecture.md#performance-bar). API output is unchanged: the new tests compare the new code with a copy of the M7.1b code over generated corpora, and `bun run check` and `bun run test:reference` pass.

## What changed

| # | Change | Where | Gain |
|---|---|---|---|
| 1 | **JSON writer.** `Record.marshalJSON` writes the members itself: no `Map` to object copy (`setOwn` = `defineProperty` per member), no entries array, no sort and no quote per record. The sorted member order and the pre-quoted names are computed once per field list (`recordJSONLayout`, checked against the field objects and names on every use, so a rename or hide cannot leave a stale layout; collections with a name that needs escaping or a field named `expand`, `collectionId`, `collectionName`, and records with custom data go through the generic path). Strings with nothing to escape are copied between quotes (one regex test); a marshaler's output (a `json` field, a date) that is already compact and canonical is checked in one pass without allocation (`isCanonicalCompactJSON`) and used as it is instead of parsed and rebuilt; nested records are trusted (`canonicalJSON`). `Object.entries` arrays are gone from the object path. | `src/tools/types/go-json.ts`, `src/records/record-json.ts` (new), `record-model.ts` | 30-record list with an expand level, JSON only: 1,100 µs to 170 µs |
| 2 | **Read-pool batching.** When more reads wait than workers are idle, an idle worker takes up to 4 queued reads in one `postMessage` (each is still answered on its own). A request alone is posted alone, as before. An idle worker takes over reads that wait behind a request running over 10 ms (the first worker's answer for them is dropped; reads can be repeated), so a slow query cannot hold up its batch partners; a read that times out while it waits behind another fails at its own deadline (D8) and its answer is skipped; when a worker is retired for a timeout the reads that did not run go back to the queue. Same pool size, same `--queryTimeout` behavior. | `src/db/read-pool.ts`, `read-worker.ts` | pool micro-benchmark, 50 concurrent loops, 4 workers: `select 1` 46k to 90k reads/s, 30-row `select *` 16k to 24k reads/s |
| 3 | **Log row export.** The generic object path above now also writes the request log attrs (`Object.keys` and a values array instead of entry pairs, fast quote). The byte counts of the message, the data and `cutStr` are skipped when `length * 3` is under the limit (a UTF-16 unit is at most 3 bytes). The log time is formatted from `toISOString` for years 1000 to 9999. No dedicated attrs builder was written: the generic path is within a microsecond of what one would give. | `go-json.ts`, `src/logs/log-model.ts`, `src/middlewares/activity-logger.ts` | `logDBExport` of a request log: 6.3 µs to 2.6 µs |
| 4 | **Per-request overhead.** `ValidationErrors` (so every `new Errors()` of the validation chain, one per field validated) and `JsonEOFError` (thrown on each incomplete prefix while a request body is read) no longer capture a stack trace: that was the `Error` native of the create profile (about 3% of it). `cleanSlashPath` returns an already clean rooted path without splitting it; the IPv4-mapped regex only runs for `::` addresses; a single response chunk is the `Response` body as it is (no `Blob`). | `src/server/error.ts`, `json-decode.ts`, `mux.ts`, `serve.ts`, `router.ts` | below the noise on `/api/health` and create (see the verdict) |

**`logSQL` needed no change.** `queryLogFunc?.(ms, this.logSQL(), err)` does not evaluate its arguments when there is no function, and the function is set only in dev mode (`--dev`, or any run from source). The `logSQL` in the M7.1a and M7.1b profiles (2.5% of the expand profile) is an artifact of profiling `src/main.ts`, which is a dev run that also prints every log line. `bench.ts --cpu-prof` now passes `--dev=false`, so profiles match the compiled executable.

Left out: the expand driver (#6 of the M7.1b ranking) and `Object.entries` in `fieldsData` (#5): not asked in this brief's list and the new profile does not rank them first.

## Tests added

- `test/tools/types/go-json-writer.test.ts`: 6,000 generated JSON texts (odd spacing, `\/`, `é`, uppercase hex, lone surrogate escapes, numbers like `01` and `1.`, mutated and truncated) and 4,000 generated values (nested maps, objects with integer-like keys, `__proto__`, astral and private-use names, bigints, `-0`, `JSONRaw`) written by the new and the M7.1b writer under five option sets (including `legacy`): same text, same error, same partial output. `isCanonicalCompactJSON` accepts only text that the old reformatting leaves unchanged.
- `test/records/record-json-writer.test.ts`: 600 generated records (every field type, hidden and unhidden fields, custom data, auth collections with and without email visibility, expands nested three levels) against `marshal(publicExport())` of the M7.1b writer, also as part of a larger value; a field list changed between two writes (rename, hide, add, remove, field named like a helper member, names needing escapes).
- `test/logs/log-export.test.ts`: 3,000 generated request logs (unicode, lone surrogates, huge messages and data that get truncated, times at the edges of years 1000 and 9999 and invalid dates) through the old and the new `logDBExport` with five size limits: the same row.
- `test/server/clean-path.test.ts`: `cleanSlashPath` against `path.Clean` over 20,000 generated paths.
- `test/db/read-pool.test.ts`: 120 queued reads with failures among them each get their own result; a slow read does not hold up the reads posted behind it (fails without the takeover); a read posted behind a slow one fails at its deadline and the pool goes on.
- `test/tools/types/go-json-before-m71c.ts` and `test/logs/log-model-before-m71c.ts` are copies of the M7.1b code, the references of these tests.

## Profiles

Microbenchmarks of one item each are above. The effect on the whole is the table: list and expand 1.3 to 1.6× the throughput of before, view 1.27×.

**What remains: create.** Profile of the source (`--dev=false`, 50 clients, 8 s): the SQLite insert (`run`, native) is 16.9% self, the request body stream natives (`onRSDefaultController*`) 4.8%, JSON body decoding (`json-decode.ts` `string`, `object`, `setOwn`) about 3.5%, the record save chain the rest; the `Error` native is gone. The insert and its commit run synchronously on the main thread (the write connection), while upstream commits on a Go thread beside its request threads, so upstream's create keeps scaling with cores (2,938 req/s at 50 clients against 1,775) while ours is one thread at 100% of one core with the other cores idle. That is single thread against many cores: moving writes to a thread is a different design (D8 keeps the writer on the main thread) and multi-process or multi-thread serving is ruled out by the owner. The p95 is within the bar (1.12).

**List and expand** are now close to upstream at p50 and faster at p95; what is left in the profile is the read-pool hop (`postMessage` is still the largest native self time, about half of what it was), hydration (`hydrateRecord`) and the `publicExport` of expand records, each a few percent.
