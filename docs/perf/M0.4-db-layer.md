# M0.4 database layer: baseline

First implementation of `src/db`, so there is no "before". Later changes to the database layer compare against these numbers, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-27 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Disk | ext4 on `/dev/sda1` (the repository's disk, not tmpfs) |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Commit | `task/M0.4-db-layer` |

## Method

`bun test/db/bench.ts --dir .upstream/bench` after `bun run upstream:prepare`, run with `nice -n 10` while the host was otherwise idle. Each run copies upstream's `tests/data` into a new scratch directory, opens it with `Databases.open` (upstream's pragmas: WAL, `synchronous=NORMAL`) and removes it afterwards.

- **Open:** `Databases.open` on a fresh copy, which opens `data.db` and `auxiliary.db` and applies the pragmas on each. Median of 20 copies.
- **Insert:** `app.db().insert("bench", {id, title, n}).execute()` into a three-column table with a text primary key. "Outside a transaction" is one implicit transaction per row (2,000 rows); "inside" is 20,000 rows in one `runInTransaction`.
- **Select:** `app.db().select("id", "title", "n").from("bench").where(new HashExp({id})).limit(1).one()`, 20,000 lookups by primary key, outside and inside one transaction. Each call builds the query (dbx SQL text, placeholder processing) and runs it on the cached statement.
- **10,000-row select:** `select(...).from("bench").limit(10_000).all()` returning row objects. Median of 20.

Both concurrent and nonconcurrent builders run on the main-thread connection (M0.6 decides D8).

## Lossless integers (council round 1)

Statements now run with bun:sqlite's `safeIntegers`, and the row readers narrow every integer inside `Number.MAX_SAFE_INTEGER` to a number (integers outside it stay `bigint`; see `src/db/dbx/rows.ts`). Rows are stepped one at a time for `row()`, `column()` and iteration. Same machine and method, measured on 2026-10-27 right before and after the change; three runs after, ranges shown.

| Measurement | Before | After |
|---|---|---|
| Open `data.db` + `auxiliary.db` (median of 20) | 0.81 ms | 0.75–0.80 ms |
| Single-row insert, outside a transaction | 18,774 ops/s | 25,614–25,823 ops/s |
| Single-row insert, inside one transaction | 108,568 ops/s | 118,284–123,517 ops/s |
| Single-row select by id, outside a transaction | 100,921 ops/s | 81,460–108,545 ops/s |
| Single-row select by id, inside one transaction | 162,559 ops/s | 123,416–164,645 ops/s |
| 10,000-row select (median of 20) | 2.73 ms | 3.29–3.59 ms |

The 10,000-row select costs about 0.6 ms more (20–30 %): the integer check and conversion on every value. `safeIntegers` alone does not change the read time measurably; comparing `Number(v)` with `Number.isSafeInteger` was cheaper than comparing bigints against the bounds. The single-row numbers vary by more than the difference between runs, and inserts do not read rows.

## SQL scripts, exact rowids and own row statements (council round 2)

Queries now run a SQL text with several statements as Go's SQLite driver does (`src/db/dbx/driver.ts`): Execute() reports `changes()` and `last_insert_rowid()` after the last statement (one extra cached `SELECT` per execute), single statements are executed on the connection's cached statement instead of `Database.run`, and text without a semicolon skips the statement splitter. `rows()` prepares a statement of its own; `one()`, `all()`, `row()` and `column()` keep the cached one. Same machine and method, measured on 2026-10-28 with the previous head (`f3fd190`) and this change in alternating runs; three runs each, ranges shown. The host was busier than on 2026-10-27, so the ranges are wide.

| Measurement | Before (`f3fd190`) | After |
|---|---|---|
| Open `data.db` + `auxiliary.db` (median of 20) | 0.76–0.83 ms | 0.79–0.81 ms |
| Single-row insert, outside a transaction | 23,656–25,645 ops/s | 18,278–26,456 ops/s |
| Single-row insert, inside one transaction | 104,910–108,744 ops/s | 100,158–154,124 ops/s |
| Single-row select by id, outside a transaction | 84,226–113,012 ops/s | 75,030–96,104 ops/s |
| Single-row select by id, inside one transaction | 128,320–160,533 ops/s | 100,304–139,467 ops/s |
| 10,000-row select (median of 20) | 3.27–3.48 ms | 3.12–4.19 ms |

The ranges overlap. In isolation (an in-memory database, 20,000 calls), running the cached statement takes 1.75 µs per insert against 3.98 µs for `Database.run`, and the `changes()` read takes 0.35 µs. Splitting a statement without a semicolon takes 0.06 µs. A first version that split every text with the full tokenizer (1.4–1.9 µs) and prepared a statement for every execute was 25–40 % slower; both were fixed before these measurements.

## Notes

- Inserts outside a transaction are bounded by the WAL commit per row (`synchronous=NORMAL` does not fsync on each commit, but each commit still writes a WAL frame and takes the write lock).
- Selects outside a transaction start and end an implicit read transaction per statement, and `app.db()` creates the routing builder on each call, as upstream's `DB()` does.
