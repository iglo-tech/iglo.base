# M3.3: batch API

`POST /api/batch` runs its items synchronously on one transaction (D28), and the record create, update and delete handlers became steps behind one `RecordIO` so that the routes and the batch share them. Two questions: how does a batch compare with upstream, and did the shared handlers slow the single-request routes?

## Setup

| | |
|---|---|
| Date | 2026-10-30 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; 10–12 GiB available during the runs) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`) |
| Commits | before `ac5d54f` (`main`), after `task/M3.3-batch` |

One measurement at a time, with MemAvailable watched (it stayed above 10 GiB). Other work may have run on the host, so differences within a run's noise mean nothing.

## 50-item batches

`nice -n 10 bun test/perf/batch/bench.ts` (100 batches per workload, one in flight, after 10 warm-up batches; a guest, over keep-alive `fetch`). A fresh install built through upstream's API; `notes` has empty rules and `notes_rel` a relation rule (`team.name != "Team 3"`) on create, update and delete. Each server serves its own copy, one after the other.

| Workload | Upstream items/s | Upstream p50 / p99 per batch | iglo.base items/s | iglo.base p50 / p99 per batch |
|---|---|---|---|---|
| create | 2,376 | 20.2 / 43.7 ms | 3,599 | 12.7 / 31.7 ms |
| update | 1,729 | 26.3 / 80.9 ms | 2,633 | 17.4 / 51.2 ms |
| delete | 4,020 | 12.1 / 21.0 ms | 6,677 | 6.5 / 17.3 ms |
| create, relation rule | 1,632 | 29.0 / 56.7 ms | 2,294 | 20.1 / 40.8 ms |
| update, relation rule | 1,611 | 29.1 / 69.8 ms | 2,496 | 18.8 / 59.8 ms |
| delete, relation rule | 3,005 | 15.9 / 30.2 ms | 3,736 | 12.0 / 30.3 ms |

iglo.base is 1.2–1.7 times upstream's item rate at one batch in flight: an item's reads are direct synchronous calls on the transaction's connection, without upstream's internal multipart request per item. The event loop is blocked for the whole batch (D28): about 20 ms for 50 updates here, and every other request waits that long. That cost grows with `batch.maxRequests` and with what the items do; bcrypt on auth items is the expensive case.

Item sizes stay small in memory: an item's File keeps only its first bytes, and upload data past the form's memory limit stays in the request's temporary file (D27). `test/batch/batch.test.ts` checks that files are stored from it and that it is gone after a success and a failure.

## Answer

A batch is faster than upstream's on this host at one batch in flight, at the cost D28 names: the event loop is blocked while it runs. The generator steps show no measurable slowdown on the single-request routes.
