# M3.1 records create, update and delete

First records write endpoints, so there is no "before". Later changes to the write path compare against these numbers, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-29 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Upstream | PocketBase v0.41.0 release binary (Go 1.27.2) |
| Commit | `task/M3.1-records-write` |

## Method

`nice -n 10 bun test/perf/records-write/bench.ts --concurrency <n>`, with the host otherwise idle. The script builds one fresh install through upstream's API: 10 teams and 50 members (auth, `team` relation), and two collections with the same fields (`title`, `views`, `author` relation, `created`/`updated`): `notes` (create, update and delete rule `""`) and `notes_rel` (rule `author.team.name != "Team 3"` for all three, a two-join relation rule; on create it is checked against the submitted record). Upstream and the iglo.base executable then each serve a copy of that pb_data in turn. As a guest over keep-alive `fetch` connections, each collection gets 200 warm-up creates, then 2,000 creates with explicit ids, an update of each created record (`title` and `views+`) and a delete of each, with `n` requests in flight. The client is Bun on the same machine.

## Results

Requests/s, p50 and p99 latency.

| Workload | Upstream, 1 in flight | iglo.base, 1 in flight | Upstream, 8 | iglo.base, 8 |
|---|---|---|---|---|
| create | 1,067/s, 0.98 / 2.10 ms | 1,267/s, 0.56 / 3.64 ms | 5,503/s, 1.26 / 4.58 ms | 2,096/s, 3.17 / 10.37 ms |
| update | 689/s, 1.41 / 2.75 ms | 857/s, 0.99 / 3.56 ms | 4,590/s, 1.56 / 4.39 ms | 1,738/s, 4.08 / 11.47 ms |
| delete | 1,147/s, 0.87 / 1.67 ms | 1,661/s, 0.56 / 1.21 ms | 5,791/s, 1.19 / 4.42 ms | 4,081/s, 1.66 / 5.28 ms |
| create, relation rule | 695/s, 1.36 / 2.85 ms | 849/s, 1.02 / 3.79 ms | 4,389/s, 1.60 / 4.88 ms | 1,756/s, 4.02 / 10.85 ms |
| update, relation rule | 678/s, 1.57 / 3.06 ms | 764/s, 1.11 / 4.09 ms | 4,722/s, 1.51 / 4.28 ms | 1,746/s, 4.16 / 11.08 ms |
| delete, relation rule | 897/s, 1.10 / 2.13 ms | 1,306/s, 0.67 / 1.72 ms | 5,921/s, 1.16 / 3.90 ms | 3,633/s, 1.89 / 5.62 ms |

- One request at a time, iglo.base is ahead of upstream on every workload (p50 0.6–1.1 ms against 0.9–1.6 ms); its p99 is higher on create and update.
- With 8 in flight, upstream spreads the requests over the 6 cores (the writes themselves are serialized by SQLite in both). iglo.base runs the handler, validation, the save chain and the JSON on its one event loop, so it stops near 2,000 creates/s and 1,750 updates/s, about 40% of upstream; deletes, which do the least work outside SQLite, reach 70%. This is the same limit as the read path (docs/perf/M2.4-records-read.md) and is left for M7.
- The record reads and the create, update, delete and manage rule checks run on the read worker pool; an update reads the record twice (without and with the rule), as upstream does.
