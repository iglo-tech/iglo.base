# M0.7 spike: thumbnails without native addons (D10)

Which library makes upstream v0.41.0's thumbnails in iglo.base, inside the compiled executable? The comparison covers executable size, memory and time on large originals, and how close the output is to upstream's thumbnails.

## Setup

| | |
|---|---|
| Date | 2026-10-30 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory (2–16 GiB; MemTotal 15.6 GiB, about 8.4 GiB available at the start) |
| Bun | 1.4.4 (`Bun.Image`: libjpeg-turbo, spng, libwebp, built-in GIF and BMP decoders, Highway SIMD resize) |
| Upstream | PocketBase v0.41.0 release binary (`.upstream/bin/pocketbase`): disintegration/imaging v1.6.2, golang.org/x/image v0.47.0 (WebP decoder), Go 1.27 |
| Command | `nice -n 10 bun scripts/spikes/M0.7/run.ts` (about 20 minutes, most of it the wasm-vips timeouts) |

## What upstream does

`createThumb` in `tools/filesystem/filesystem.go`:

1. Parses the size with `ThumbSizeRegex` (`^(\d+)x(\d+)(t|b|f)?$`); `0x0` is an error.
2. Reads only the header (`image.DecodeConfig`). If width × height is over `PB_THUMBS_MAX_SOURCE_PIXELS` (default `100 << 20` = 104,857,600), it fails before the full decode.
3. Decodes with `imaging.Decode(r, imaging.AutoOrientation(true))`: Go's JPEG, PNG and GIF decoders (first frame), x/image's BMP, TIFF and WebP decoders. The EXIF orientation comes from the first APP1 segment of a JPEG only.
4. Resizes with `imaging.Linear` (a triangle filter whose support grows with the reduction, so it averages every source pixel). `0xH`/`Wx0`: `Resize`. `WxHf`: `Fit`, which never enlarges. `WxH`, `WxHt`, `WxHb`: `Fill` with the center, top or bottom anchor. For sources of at least 100×100 px, `Fill` crops first and then resizes (`cropAndResize`); smaller sources are resized first and then cropped.
5. Encodes by the original's stored content type: `image/jpeg` as JPEG quality 95, `image/gif` as GIF (Plan 9 palette, Floyd–Steinberg dithering, no transparency), `image/tiff` as TIFF (deflate), `image/bmp` as BMP. Everything else, WebP included, becomes PNG (default compression), stored as `image/png`.

`apis/file.go` calls `CreateThumb` only for originals whose content type is `image/png`, `image/jpg`, `image/jpeg`, `image/gif` or `image/webp` (`imageContentTypes`), and only for `100x100` or a size in the field's `thumbs`. TIFF and BMP originals are never thumbed: upstream serves the original. Their decoders and encoders are not reachable through the API. Generation is deduplicated per thumb path (singleflight) and limited by a semaphore of `PB_THUMBS_MAX_WORKERS` (default NumCPU + 2). A request that waits longer than `PB_THUMBS_MAX_WAIT` (default 60 s) to start fails. On any error the original is served (status 200), and a warning is logged.

## Candidates

All run the same steps 1–5 and are measured the same way. Each candidate's code is in `scripts/spikes/M0.7/candidates/`.

| jsquash | `@jsquash/jpeg` 1.6.0 (MozJPEG), `@jsquash/png` 3.1.1, `@jsquash/webp` 1.5.0, `omggif` 1.0.10 | the port | MozJPEG q95 baseline, `@jsquash/png`, the GIF port | Apache-2.0 (jsquash), MIT (omggif) |

All candidates share the spike's header check, error texts and plan of the geometry (`thumbPlan`), so the dimensions are computed with upstream's arithmetic everywhere.

Other options looked at: Bun 1.4.4 has no other image API. Pure JavaScript codecs (`jpeg-js`, `pngjs`, `fast-png`) would need a WebP decoder from elsewhere and are slower than the wasm codecs. `@cf-wasm/photon` (6 MB) and `imagescript` (AGPL-3.0 or MIT) cover no more formats than jsquash. None was measured.

## Method

- **Executables.** `bench.ts` is compiled with one `workers/worker-<candidate>.ts` into its own executable (`bun build --compile`), so every candidate runs as M5.2 would ship it: in a compiled executable, inside Bun Workers. A build with an empty worker is the size baseline. Codec `.wasm` files are embedded with `import … with { type: "file" }`.
- **Quality.** `images.ts` generates 17 originals from coordinates and a seeded PRNG: a 640×427 "photo" (smooth color fields, a disk, a sharp-edged block, a band of 2-px stripes, noise) as baseline, progressive, 4:4:4, grayscale, CMYK and EXIF-orientation-6 JPEG; RGBA, alpha-gradient, indexed+tRNS and 16-bit gray PNG; a 60×40 PNG (the resize-then-crop path); lossy and lossless-with-alpha WebP; GIF and GIF with a transparent index; BMP and TIFF. Upstream makes 10 sizes of each through the files API (`100x100`, `70x50`, `70x50t`, `70x50b`, `70x50f`, `0x50`, `70x0`, `500x500f`, `800x0`, `1200x0`). They include enlargement and a fit larger than the source. Each candidate makes the same 150 thumbs in one worker. Both outputs are decoded by the same decoder (`Bun.Image`). The comparison checks dimensions, content type, and the mean absolute error (MAE) per channel on a 0–255 scale: R, G, B premultiplied by alpha, then A. A second MAE is taken after a 3×3 box blur of both images. Floyd–Steinberg dithering turns a small input difference into a different dot pattern, which the plain per-pixel MAE counts in full.
- **Edge cases.** A JPEG cut at half its scan data, a JPEG without its final EOI marker, a JPEG with 0xFF bytes written into its scan data, a PNG cut in its IDAT, a PNG with a corrupted IDAT byte, and a PNG header claiming 11000×10000 (110 MP) with 1 px of data.
- **Speed and memory.** The originals are a 50-megapixel JPEG (8660×5773, q90, 14.7 MiB) and a 12-megapixel PNG (4240×2832, 26.3 MiB), with the same generated content, made into `100x100` and `1200x0` thumbs. At concurrency 1 there is one worker and one thumb. At concurrency 4 there are four workers and four thumbs of the same original at once. Each measurement runs in a fresh process, one at a time. The workers are started and warmed first: the codecs compile their wasm on a 4×4 image. Peak RSS is the process's `VmHWM`, which covers the workers' threads. "Idle" is `VmRSS` after the warm-up. Upstream gets 4 records per original. Each measurement uses a freshly started server, with the previous thumbs deleted, and four concurrent `GET …?thumb=` requests to different records. A measurement is killed when MemAvailable drops under 2 GiB; that never happened.

Go's `image/jpeg` reads marker after marker until EOI and fails with `unexpected EOF` when the data ends first, also inside a scan. `Bun.Image` decodes such files. The first run, before the check, made thumbs of both cut JPEGs with every candidate. `checkJpegComplete` (`orient.ts`) walks the same markers: segments by their length, entropy-coded data up to the next marker that is not a stuffed 0xFF00, fill or RSTn. It costs 0.2 ms on a 640×427 JPEG. With it, the Bun candidates fail on the same 6 originals as upstream. The pixel limit is applied on the header: `Bun.Image`'s `maxPixels` refuses before allocating, and the spike repeats upstream's `>` check and message.

- **The exact path's memory.** bun-imaging decodes the whole original into JavaScript. A 50 MP JPEG costs 1.1 GiB per thumb, about 23 bytes per source pixel: the decoded pixels, the uncompressed PNG that carries them out of `Bun.Image`, its inflated rows, and the fill crop's copy. Four at once peaked at 4.5 GiB against upstream's 0.8 GiB. With upstream's default `PB_THUMBS_MAX_WORKERS` (NumCPU + 2, 8 on this host), eight such originals at once would not fit a 2 GiB host. Its speed is 2.5× upstream's time on the 50 MP JPEG and 1.4× on the 12 MP PNG.
- **Native pre-reduction removes most of that.** bun-hybrid makes 100x100 from 50 MP in 0.24 s and 72 MiB, 4.5× faster and 3× smaller than upstream. For `1200x0` it is close to upstream: 1.2 s and 404 MiB against 1.05 s and 140 MiB. `Bun.Image` decodes a JPEG reduced to half or less at a 1/2–1/8 DCT scale, so the full-size pixels never exist. A PNG cannot be decoded at a smaller scale, but its full-size pixels then stay inside `Bun.Image` and never reach JavaScript.
- **jsquash** is faster than bun-imaging on the 50 MP JPEG (MozJPEG in wasm, without the PNG round trip), but every worker carries its own wasm heaps (about 11 MiB per idle worker: 52 MiB with 1, 85 MiB with 4), and it fails on CMYK JPEG.
- **wasm-vips 0.0.19 does not run under Bun 1.4.4.** It initializes (with `dynamicLibraries: []`; with its default HEIF, JPEG XL and SVG side modules it does not even do that) and reads headers. The first pixel operation then hangs, also with `concurrency(1)`, because its pthread Workers (`node:worker_threads` with `workerData: "em-pthread"`) never make progress. The same script works under Node 20.19.

## Answer

**Choice: Bun's built-in `Bun.Image` (Bun ≥ 1.4) for decoding and the JPEG and PNG encoders, with upstream's resize, crop and GIF encoding ported to TypeScript.** It adds no runtime dependency and no bytes to the executable: the codecs (libjpeg-turbo: IJG/BSD-3-Clause/zlib; spng: BSD-2-Clause; libwebp: BSD-3-Clause) are part of the Bun runtime (MIT) that every iglo.base executable already contains. The ported code is MIT (disintegration/imaging) and BSD-3-Clause (Go), and M5.2 adds their notices to `LICENSE`. Measured against upstream's own thumbnails, the dimensions and content types are equal for all 150 thumbs. PNG, GIF and lossless WebP originals give identical pixels. JPEG differs by about 1/255 and lossy WebP by 5–8/255 per channel, both from the decoders, not the geometry. jsquash (0.9 MiB, fails on CMYK JPEG, ~2× the JPEG error), wasm-vips (5 MiB, hangs under Bun) and sharp (native, not embeddable, not upstream's geometry) are not needed.

**What M5.2 must do:**

1. **Worker pool.** Run thumbs in Bun Workers: the TypeScript resize and the GIF dithering are CPU-bound, and `Bun.Image` itself already decodes and encodes off the JavaScript thread. Keep upstream's rules from `apis/file.go`: only the five `imageContentTypes`, only `100x100` and the field's `thumbs`; one generation per thumb path at a time (singleflight); a semaphore of `PB_THUMBS_MAX_WORKERS` (default NumCPU + 2); `PB_THUMBS_MAX_WAIT` (default 60 s) to start; serve the original, with a warning in the app log, on any error. A warm Bun Worker adds about 4 MiB (idle RSS 34 MiB with 1 worker, 47 MiB with 4). Start the workers lazily, up to the semaphore's size.
2. **Steps, in upstream's order.** Parse the size (`ThumbSizeRegex`, `0x0` error). Read the header with `new Bun.Image(bytes, { maxPixels }).metadata()`, with `maxPixels` set to the `PB_THUMBS_MAX_SOURCE_PIXELS` limit. It reports the size after the EXIF orientation and refuses before allocating. Repeat upstream's `width × height > max` check and its error text. Run the JPEG end-of-data check (`checkJpegComplete`, a walk to EOI) so cut JPEGs fail as Go's decoder fails. Decode with `autoOrient` (the default). Do the geometry with the port of imaging's `Resize`, `Fit`, `Fill` (`cropAndResize` and `resizeAndCrop`), `CropAnchor` and the `Linear` filter, as in `scripts/spikes/M0.7/imaging.ts`. Encode JPEG at quality 95 and PNG with `Bun.Image`, and GIF with the port of Go's `gif.Encode` (Plan 9 palette, Floyd–Steinberg, LZW) in `gif.ts`. The content type follows `createThumb`'s switch.
3. **Bound the memory** (lead decides the threshold). The exact path needs about 23 bytes per source pixel in the worker, so a 100 MP original (the default limit) needs about 2.3 GiB. Proposal: originals up to 16 MP (≈ 370 MiB) take the exact path. Above that, reduce natively first, as bun-hybrid does: `Bun.Image` `box` resize to at least 4 source pixels per thumb pixel, then the port on the reduced pixels with the crop planned on the original's size. That adds 0.3–0.5/255 on JPEG and PNG. M5.2 can also lower the exact path's cost by inflating the uncompressed PNG into the output buffer row by row. The spike's reader already writes RGBA rows directly; the copies left are `Bun.Image`'s PNG bytes and the inflate output.
4. **Formats the choice cannot match, and the fallback.** None that the API reaches. TIFF decode is unavailable on Linux, and there are no TIFF or BMP encoders, but upstream never thumbs `image/tiff` or `image/bmp` originals (`imageContentTypes`). M5.2 serves the original for them, as upstream does. Lossy WebP thumbs differ by up to about 8/255 per channel, from libwebp's decoder against x/image/webp's. This is a perceptual difference only, and the acceptance test's tolerance must allow it. A pixel match would need a port of golang.org/x/image/vp8, a backlog item if the owner wants it. Not tested here: GIFs whose first frame is smaller than the logical screen (Go's decoder returns the frame's bounds), and JPEGs whose first APP1 segment is not Exif (imaging then ignores the orientation). M5.2's tests should cover both against upstream.

`Bun.Image` is new in Bun 1.4. Its behavior on damaged JPEGs (it decodes with a warning where Go fails) is the only difference found that changes what a client receives, and the EOI check covers it. Run this spike again when the pinned Bun version changes.
