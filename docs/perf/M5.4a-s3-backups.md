# M5.4a S3 backups: measurements

Run on 2026-11-01 on the shared host (6 cores, other work running), with Bun 1.4.4 and upstream v0.41.0, on a work directory on disk, against a local versitygw (posix backend, same disk). Script: `test/perf/backups/s3.ts`.

## A 1 GiB backup

The fixture plus 1 GiB of random bytes in 64 storage files, so the zip is 1,024 MiB on both servers, well above upstream's 6 MiB part size. Each server ran on its own copy and bucket. RSS is sampled every 20 ms. Download and upload use curl. The restore time runs from the request until a marker record is gone after the restart, and includes each server's 1 second wait.

| | iglo.base | upstream |
|---|---:|---:|
| Create (zip and multipart upload), time | 18.3 s | 5.1 s |
| Create: RSS before, peak | 82, 272 MiB | 33, 105 MiB |
| Download, time | 5.0 s | 1.5 s |
| Download: RSS before, peak | 132, 183 MiB | 75, 75 MiB |
| Upload through the API, time | 13.7 s | 11.6 s |
| Upload: RSS before, peak | 139, 353 MiB | 42, 171 MiB |
| Restore, time | 12.1 s | 9.6 s |
| Restore: RSS before, peak | 169, 169 MiB | 140, 147 MiB |

Request latency: `GET /api/collections/demo1/records?perPage=1`, one after the other with 5 ms between them.

| | requests | p50 | p99 | max |
|---|---:|---:|---:|---:|
| iglo.base, during create | 2,117 | 1.8 ms | 24.5 ms | 52.8 ms |
| upstream, during create | 589 | 1.6 ms | 18.9 ms | 50.4 ms |
| iglo.base, during download | 597 | 1.6 ms | 23.3 ms | 48.9 ms |
| upstream, during download | 158 | 2.5 ms | 16.1 ms | 17 ms |
| iglo.base, during upload | 1,255 | 1.6 ms | 78.2 ms | 438.2 ms |
| upstream, during upload | 1,406 | 1.4 ms | 18 ms | 73.4 ms |

- Memory stays bounded: a zip of 1 GiB adds at most about 215 MiB over the process before it, part of it uncollected part buffers. The upload holds at most five 6 MiB parts; download and restore go to disk in the pieces `fetch` delivers. The restore's peak is at the sample before the step, so the transfer added nothing visible.
- Create is 3.6× upstream's time. Most of that is the zip: random bytes through `node:zlib`, already 1.6–2× upstream in M5.3 (`docs/perf/M5.3-backups.md`). The upload itself is the part of it the API upload row shows.
- Download is 3.3× upstream's: Bun drops `Content-Length` on a streamed body, so the bytes are spooled to a temp file and then sent. A 1 GiB download takes a further 1 GiB of disk for that time, and the client's first byte comes after the spool. See [API compatibility](../design/04-api-compatibility.md#deliberate-differences).
- The stalls in the upload row are not the S3 client. The same uploader ran during create with a 52.8 ms maximum. The same 1 GiB file uploaded to local backups, with no S3 and a body of random bytes, gave p99 62 ms and max 161 ms, the worst at the very end of the request. That is the multipart intake and its temp file (M3.2, D27), which this task does not own. On the backlog for M7.1.
