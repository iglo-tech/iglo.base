# M2.1 search: fexpr and tools/search

First implementation of the filter language (`src/search/fexpr/`) and of `tools/search` (`src/search/`), so there is no "before". Later changes to filters compare against these numbers, measured the same way.

## Setup

| | |
|---|---|
| Date | 2026-10-28 |
| Machine | AMD Ryzen 5 1600 (6 cores), 16 GiB RAM, Linux 6.12 (Debian 13), VM |
| Bun | 1.4.4 (bundled SQLite 3.53.4) |
| Commit | `task/M2.1-search` |

## Method

`nice -n 10 bun test/search/bench.ts`, with the host otherwise idle. Each figure is the median of the runs after warm-up runs.

- **Parse + build:** `filterBuildExpr` with the simple field resolver (`title`, `n`, `active`, `created`), then `Expression.build` to the SQL text: tokenizing, parsing, resolving, the placeholder params and the SQL. 2,000 runs after 200 warm-up runs, without and with a `ParsedFilterCache` (upstream's parse cache, which skips the tokenizer and parser on a repeated filter).
- **Provider list:** `Provider.exec` with the simple field resolver over a 10,000-row table (`id`, `title`, `n`, `active`, `created`; no indexes besides the primary key) in a WAL file database in the OS temp directory, on the main-thread connection. The count and the page query both run unless `skipTotal`. Rows are returned as plain objects (no model hydration). 50 runs after 5 warm-up runs.

## Results

Two runs; the second in parentheses.

| Filter | Length | No cache | With cache |
|---|---|---|---|
| simple (`title = 'abc'`) | 13 | 0.015 ms (0.013 ms) | 0.005 ms (0.007 ms) |
| 50 expressions (`&&` of `>`, `~`, `= true`) | 720 | 0.32 ms (0.36 ms) | 0.19 ms (0.19 ms) |
| nested groups (depth 10) | 284 | 0.30 ms (0.27 ms) | 0.09 ms (0.09 ms) |
| long string (`~` with 3,000 characters) | 3,010 | 0.32 ms (0.29 ms) | 0.18 ms (0.18 ms) |
| macros and functions (`@todayStart`, `strftime`, `geoDistance`) | 90 | 0.058 ms (0.062 ms) | 0.034 ms (0.030 ms) |

| Provider list over 10,000 rows | Time |
|---|---|
| no filter, page 1 of 30, with count | 0.62 ms (0.56 ms) |
| filter (`n > 2500 && title ~ 'title 1' && active = true`) + sort (`-n,title`), page 1 of 30, with count | 2.55 ms (2.93 ms) |
| filter + sort, 1,000 rows, `skipTotal` | 10.2 ms (9.8 ms) |
| all 10,000 rows (10 pages of 1,000), `skipTotal` | 33.0 ms (29.7 ms) |

- Parsing and building stay well under a millisecond up to the filter length limit (3,500 characters) and a quarter of the expression limit (200); the cache roughly halves the cost of a repeated filter. Neither is significant next to the queries.
- The Provider's own work (filter, sort, the count query) is small; the list cost is SQLite reading and returning the rows. Record hydration and JSON encoding come with the records endpoints (M2.4), which measure endpoint against endpoint with upstream.

## Number literals bound as REAL (fix round 1)

A number token is now a dbx `Float64` param, and dbx runs a query with one of those with its placeholder written as `+CAST(? AS REAL)` (the SQL text is processed once more per execution). Measured as above, same day and machine. The filter + sort case has `n > 2500`, a number literal.

| Case | Before | After (second run) |
|---|---|---|
| parse + build, 50 expressions, no cache | 0.28 ms | 0.29 ms (0.31 ms) |
| parse + build, macros and functions, no cache | 0.057 ms | 0.055 ms (0.056 ms) |
| Provider: filter + sort, page 1 of 30, with count | 2.56 ms | 2.48 ms (2.40 ms) |
| Provider: filter + sort, 1,000 rows, `skipTotal` | 9.31 ms | 10.00 ms (9.50 ms) |

The differences are within run-to-run noise.
