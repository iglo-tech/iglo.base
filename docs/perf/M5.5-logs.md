# M5.5: request logs

What do request logs cost a read route, against the build before them and against upstream v0.41.0 with logging on, and does memory stay bounded under a sustained burst?

## Setup

| | |
|---|---|
| Date | 2026-11-02 |
| Machine | AMD Ryzen 5 1600 (6 cores), Linux 6.12 (Debian 13), VM with dynamic memory, other agents running (load average about 9 at the start) |
| Bun | 1.4.4 |
| Upstream | PocketBase v0.41.0 release binary |
| iglo.base | `dist/iglo-base`: `main` at `6a43291` (before), `task/M5.5-logs` (after), 4 read workers |
| Command | `bun test/perf/logs/measure.ts <name>=<binary>...` (each server in turn); `bun test/perf/logs/parts.ts` for the cost by part |

## Method

Each server runs on its own copy of the fixture with `logs.maxDays` 7, `logIP` on, `minLevel` 0. 32 keep-alive clients in the measuring process, three rounds of 15 s per route (median of the rounds), then a 60 s burst on `/api/health`, with RSS sampled from `/proc` every 200 ms. The list route is `GET /api/collections/demo2/records?perPage=30`, guest rule `""`, on the cached collections. The client shares the machine, so `/api/health` is near its ceiling: read the ratios, not the absolute numbers.

## Results

| | before (2 runs) | after (final build) | after (3 earlier builds of this branch) | upstream |
|---|---|---|---|---|
| List route, req/s | 2,555 / 2,991 | 3,217 | 2,934 / 2,545 / 2,512 | 3,220 |
| List route, p99 ms | 53.3 / 31.2 | 24.8 | 27.8 / 37.4 / 44.8 | 64.6 |
| `/api/health`, req/s | 16,510 / 20,405 | 9,618 | 9,471 / 7,609 / 8,536 | 10,234 |
| `/api/health`, p99 ms | 8.6 / 5.0 | 14.5 | 15.3 / 21.1 / 19.0 | 15.0 |
| 60 s burst, req/s | 20,485 / 20,039 | 9,521 | 7,080 / 7,900 / 8,307 | 13,355 |
| RSS before burst → maximum, MiB | 117 → 117 / 108 → 111 | 159 → 163 | 150 → 153 / 164 → 165 / 153 → 153 | 587 → 1,299 |
| Rows in `_logs` after the run | 1 | 1,131,449 | 960,962 / 945,650 / 984,645 | 948,913 |

The earlier builds differ only in how they insert (one built statement per log, or a statement prepared again for each log), so their spread also shows the noise on this host: the same binary's list route moved between 2,512 and 3,217 req/s.

Cost of one log on the main thread (`parts.ts`, `_logs` with its indexes):

| Part | µs per log |
|---|---|
| Queueing (`handle`) | 0.5 |
| Random id | 0.6 |
| `DBExport` (JSON text, limits, date) | 5.7 |
| Insert, one prepared statement per batch | 18.8 |
| Insert, one built statement per log | 20.9 |
| Insert, one multi-row statement per batch | 20.0 |

## Reading

- **A route that does real work does not notice.** The list route's numbers before and after overlap within run-to-run noise: about 25 µs on a request of about 300 µs.
- **The cheapest route halves, to upstream's level.** `/api/health` costs about 50 µs without logs, and a log adds about 25 µs of write work on the main thread plus the attributes. It ends just under upstream's round figure.
- **The sustained burst is where upstream is ahead:** about 7–9.5k req/s against 13k. Upstream writes on other cores; here writes run on the main thread ([architecture](../design/02-architecture.md)). Nearly all of it is SQLite's insert with `_logs`' three indexes, so the insert form changes little. Moving the writer to a worker thread is the way to close it, at the cost of a build entry point and one more connection; nothing here needs it, and at 1,000 req/s the writer takes about 2.5 % of the thread.
- **Memory is bounded.** RSS holds under 170 MiB through a million rows (upstream reaches 1.3 GiB, mostly Go's heap under the same burst). The queue never holds more than the batches of one event loop turn: a batch's write runs on the next `setImmediate`.
- A batch of 200 blocks the event loop for about 5 ms. That is the p99 cost seen on `/api/health`.
