# Brief M5.4b

Written by the chief of staff on 2026-11-01 from the work plan's template. M5.4a merged the S3 client (`src/tools/filesystem/internal/s3blob/`), `S3System` (`src/tools/filesystem/s3-system.ts`) and S3 backups. Record files still go through the synchronous `System` inside write transactions (`src/fields/file.ts`, `src/records/record-save.ts`), and `newFilesystem()` throws the not-supported error when `s3.enabled` is true.

Decision from the lead: network calls never run inside a database write transaction (AGENTS.md), and the write path is synchronous (D8, D28). So with S3 enabled the files of a create, update or batch upload before the write transaction opens; if validation or the commit fails, those uploads are deleted, and the client gets the error upstream gives. Files to delete go after the commit, as upstream deletes them. Local storage keeps its synchronous path and its results. If that order cannot give upstream's result for some real request, stop and report it in the PR.
Acceptance:
  - Against versitygw from `test/support/versitygw.ts`, never a real service: files written by iglo.base are served by upstream with the same settings, and the reverse, including thumbs. Object keys, Content-Type, metadata and the bytes match upstream's as seen by a raw S3 read. Differential cases cover create, update with `+`/`-` modifiers, replace, delete, batch, record delete, collection delete and truncate, cascade delete.
  - All file scenarios that run on local storage also pass with S3 on: `GET /api/files/...` with Range, HEAD, `download`, `thumb`, conditional requests, protected files with tokens. Thumb creation under concurrent requests behaves as upstream's (one generation for one thumb), and a failed thumb falls back to the original.
  - A failed commit, a rejected validation, and an S3 failure part way through a record's uploads leave no record pointing at a missing file, answer as upstream does, and leave no orphan object where upstream leaves none. A failed S3 delete after a commit is logged as upstream logs it and fails nothing.
  - The upload's temp data and memory stay bounded: a file above the multipart threshold is streamed from its D27 spill, with concurrent requests on the same server staying responsive. No S3 call on the main thread blocks it: they are all asynchronous.
  - A backup with `s3.enabled` leaves `storage` out as upstream does; restore keeps working.
  - `POST /api/settings/test/s3` with `storage` keeps working, and turning `s3.enabled` on or off through the Settings API takes effect without a restart, as upstream's.
  - `copy-object.ts`: upstream's `CopyObjectResponse` has no `XMLName`, so any root is accepted (M5.4a review).
  - Migration bindings: `$app.newFilesystem()` keeps its current behavior with local storage; with S3 enabled a synchronous migration cannot make network calls in a transaction, so it fails with a clear error. List it in 04-api-compatibility.md.
  - The dashboard uploads, previews, thumbnails and deletes a file against versitygw: check with `agent-browser` and add the result to docs/manual-tests/dashboard.md.
  - `bun run check` and `bun run test:reference` pass locally (D25). The flakes in the hardening backlog are known; do not fix them here, and list any you saw in the PR with the rerun's result.
Out of scope: anything for backups beyond the items above, crash tests (M5.9), moving the local path off the main thread.
Measurements: docs/perf/M5.4b-s3-files.md: upload and download of a 100 MiB file, and p99 of `GET /api/health` meanwhile, against upstream through versitygw.
