```text
Task M7.3: Release workflow, the linux-x64 binary on v* tags
Goal: pushing a `v*` tag builds the one compiled executable for linux-x64 on GitHub Actions, with the version set from the tag, and attaches it with its SHA-256 checksum to a draft GitHub release; a test tag proves it end to end.
Read first: AGENTS.md (Stack, Verification), docs/design/02-architecture.md (release artifact), docs/design/10-decisions.md (D3, D18, D24, D25), docs/design/12-work-plan.md (M7.3, Rules for workers), .github/workflows/ci.yml, package.json (`build`, `ui:build`), src/cli/root.ts (`version`, "set by the release build (M7.3)") and the `--version`/`serve` banner text in docs/design/04-api-compatibility.md.
Upstream: .goreleaser.yaml and .github/workflows/release.yaml in upstream v0.41.0 (only for what a release contains: archive naming, checksums); iglo.base ships the executable itself (D3: no Docker yet; D24: linux-x64 only).
Owns: .github/workflows/release.yml (new), the version injection (src/cli/root.ts `version` and whatever build define or generated file sets it; `bun build --define` is preferred over a generated source file), package.json scripts only if the build needs a version argument, test/ for the version output, docs/design/ text about releases (02-architecture.md, and a short "Releasing" section in an existing doc or a new docs/releasing.md: how to tag, what the workflow produces, how to verify the checksum).
Depends on: M0.8 (merged).
Acceptance:
  - .github/workflows/release.yml runs on `push` of tags matching `v*` only (plus `workflow_dispatch` for a dry run that uploads a workflow artifact and creates no release). Steps: checkout, setup-bun from package.json's `packageManager` (pin actions by commit SHA as ci.yml does), `bun install --frozen-lockfile`, `bun run check` (the same gate as CI; `test:reference` is optional in the workflow if it exceeds a reasonable timeout, say so), the build with the version from the tag, a smoke test of the built executable on the runner (`--version` prints the tag's version; `serve` on a temp dir answers `/api/health` 200), then the archive and `SHA256SUMS`.
  - Artifact: `iglo-base_<version>_linux_amd64.zip` (or `.tar.gz`; pick one and document it) containing the executable `iglo-base`, `LICENSE` and a short README pointer; `SHA256SUMS` for the archive. The release is created as a **draft** (`gh release create --draft`, or the equivalent action pinned by SHA) with these files, so nothing becomes public until a human publishes it. Permissions: `contents: write` for the release job only.
  - The version: `iglo-base --version` and the `serve` banner print the tag's version without the leading `v` (`0.1.0` for `v0.1.0`) as the existing text format says, and `(untracked)` (or the current untracked form) for local builds. A test covers the local-build output; the workflow's smoke test covers the tagged one.
  - End-to-end proof on GitHub: push one test tag `v0.0.0-test.1` from your branch head, watch that workflow run to green with `gh run watch` (this is the one place in this task where waiting on GitHub is required), download the draft release's archive and checksum with `gh release download`, verify the checksum and run the downloaded executable on this host (`--version`, `serve` on a `mktemp -d` dir, `/api/health`). Then delete the draft release and the test tag (`gh release delete v0.0.0-test.1 --yes --cleanup-tag`, and `git push origin :refs/tags/v0.0.0-test.1` if the tag remains). Record the run URL and the checks in the PR body. Do not push any other tag, do not publish a release.
  - `bun run check` and `bun run test:reference` pass locally (D25). List hardening-backlog flakes seen and their rerun result.
Out of scope: macOS and arm64 builds (P.2), a Docker image (P.1), signing or notarization, publishing a release, changelogs.
Notes from the lead:
  - The repository is public: a pushed tag is visible. Only the one test tag above, deleted afterwards; the release stays a draft and is deleted.
  - Branch: task/M7.3-release. PR title: "M7.3: Release workflow for linux-x64".
  - There is no time limit; finish the task. Stop early only for a real blocker (a design conflict the lead must decide, or a usage/rate-limit error), and describe it in the PR and your reply.
```
