# Brief M7.1a

Written by the chief of staff on 2026-11-02. Owner direction (2026-11-02): no multi-process or multi-thread serving; profile first, then fix what the profile shows ([pocketbun research](../perf/pocketbun-research.md), items 1–5). M7.1 is split: M7.1a measures and profiles and does the one fix already decided (bcrypt, D27); M7.1b makes the fixes the profile justifies.

```text
Task M7.1a: Performance profile and bcrypt off the event loop
Goal: an honest, reproducible comparison of iglo.base and upstream v0.41.0 on the same host and data, CPU profiles of iglo.base's main thread showing where the time goes, a ranked list of fixes for M7.1b, and bcrypt hashing/verification moved off the event loop.
Read first: AGENTS.md, docs/design/02-architecture.md ("Performance bar"), docs/design/10-decisions.md (D8, D26, D27), docs/design/12-work-plan.md (M7.1, Rules for workers), docs/perf/pocketbun-research.md, docs/perf/M2.4-records-read.md, M3.1-records-write.md, M0.8-bcrypt.md, M5.1-realtime.md, M5.7-serve.md, and the existing benches in test/perf/ (records-read, records-write, serve, realtime).
Owns: docs/perf/M7.1a-profile.md (new), test/perf/ (a shared comparison runner if the existing benches need one; reuse them where possible), the password hashing and verification paths (src/fields/ password field, src/tools/crypto/bcrypt.ts or wherever hashing lives, the auth-with-password and record save paths that call them; only as needed to make hashing async), test/ for those paths.
Depends on: M5.8 (merged).
Acceptance:
  - Measurements, both servers, compiled iglo.base (`bun run build`) vs the pinned upstream binary, same data (a copy of the fixture plus generated rows; never write into tracked fixtures), same load tool, one server at a time, warm-up excluded: records list (guest, 30 per page; with a filter and sort; with one and two levels of expand), record view, record create (JSON), password auth (cost as in the fixture), `/api/health`; at 1, 8 and 50 concurrent clients: req/s, p50, p95, p99. Plus startup time and idle RSS, and 1,000 realtime connections with a record-change fan-out (reuse M5.1's bench). Report each with the ratio to upstream and whether it meets the bar in 02-architecture.md. State host, Bun version and noise (repeat each run 3 times, report the median).
  - CPU profiles of iglo.base's main thread (`bun --cpu-prof` on the compiled build or the source with the same flags) for list (no expand and with expand), create and `/api/health` at 8 and 50 clients. Summarize the top self-time and total-time functions with file paths, and group them (routing and middleware chain, rule/filter parse and resolve, record hydration, JSON writing, response headers, SQLite). Keep the raw `.cpuprofile` files out of git (or attach only a small summary).
  - A ranked list of fixes for M7.1b in the report: each with the profile evidence, expected gain, risk to the API/data contracts (results must stay identical), and size. Do not make those fixes here, except trivial ones (under ~30 lines, contract-neutral, with before/after numbers).
  - bcrypt off the event loop (D27): password hashing and verification use `Bun.password.hash`/`verify` (async, Bun's thread pool) or an equivalent that keeps Go's `$2a$` hash form and verifies hashes written by either server (the M0.8 cross-checks and the existing password tests must still pass). The record save path stays synchronous inside write transactions (D8, D28): compute the hash before the transaction through the existing async seam. Measure before/after: event-loop lag and `/api/health` latency during 8 concurrent cost-12 sign-ins.
  - `bun run check` and `bun run test:reference` pass locally (D25). Known hardening-backlog flakes are not fixed here; list any you saw with the rerun's result.
Out of scope: multi-process or multi-thread serving (dropped by the owner); the fixes the profile suggests beyond trivial ones (M7.1b); multipart and backup speed-ups (M7.1b if the profile ranks them).
Notes from the lead:
  - Run every benchmark one at a time, nothing else heavy in parallel (the host has limited memory and 6 cores shared with other work); note the load generator's own CPU use, and keep it in a separate process.
  - Branch: task/M7.1a-profile. PR title: "M7.1a: Performance profile and async bcrypt".
  - There is no time limit; finish the task. Stop early only for a real blocker (a design conflict the lead must decide, or a usage/rate-limit error), and describe it in the PR and your reply.
```
