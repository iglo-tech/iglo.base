Acceptance:
  - #1 (D31): `_logs` batch inserts run on one dedicated worker with its own auxiliary.db connection. Same rows and column values, same level and size rules, same 3 s tick and 200 batch, flush on app stop (serve shutdown, restart after restore, every CLI command that logs). Lock contention with the main thread (log cleanup delete, VACUUM, backup) waits and retries; no batch is dropped. Backup and restore drain and stop the writer before touching the files and start it after. Works in the compiled executable. Tests through public boundaries: logs appear in `/api/logs` with the same fields as upstream (existing differential cases), shutdown flush (logs written just before SIGTERM are in `_logs` after), a backup taken while requests are logged restores with a consistent `auxiliary.db`, and the M5.9 kill suite still passes.

  - #4: the read pool returns rows without structured-cloning one object per row (column names once, rows as arrays, or one encoded payload; measure which is cheaper). Exact integers, BLOBs, NULLs and duplicate column names behave as now.
  - #5: hydration without per-record `Object.entries`, `Map` and closure allocations where the profile shows them; same Record behavior.
