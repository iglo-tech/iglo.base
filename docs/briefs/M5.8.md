# Brief M5.8

Written by the chief of staff on 2026-11-02 from the work plan's template. Every API area the SDK calls is merged (M2–M5.7). The suite is a client-side check: it finds differences that the per-endpoint scenarios missed, as a real app sees them.

```text
Task M5.8: JavaScript SDK suite
Goal: a differential suite written with the official JavaScript SDK that calls every SDK service method against upstream v0.41.0 and iglo.base and compares the results, and fixes for the differences it finds.
Read first: AGENTS.md, docs/design/09-port-plan.md ("SDK suites"), docs/design/04-api-compatibility.md (the deliberate differences), docs/design/10-decisions.md (D22, D25, D26), docs/design/12-work-plan.md (M5.8, Rules for workers), docs/status.md (the hardening backlog), and the harness it builds on: test/differential/harness/ (run.ts, compare.ts), test/support/ (executable.ts, upstream.ts, mailpit.ts, smtp-sink.ts, oauth2-mock.ts, versitygw.ts, s3-proxy.ts, temp-root.ts), and two existing differential suites as style examples (test/differential/realtime/, test/differential/backups/).
SDK: `pocketbase` 0.28.1, the version ui/bun.lock pins for the dashboard (09-port-plan). Add it as an exact devDependency in the root package.json (test only, never imported from src/). Read its own source and types in node_modules/pocketbase (dist/pocketbase.es.d.ts and src/services/) to list the methods; do not work from memory.
Upstream (v0.41.0, .upstream/pocketbase or /home/t3-code/upstream/pocketbase, read only): the apis/*.go handlers behind any method whose results differ, to decide which side is wrong.
Owns: test/differential/sdk/ (new), small additions to test/support/ and test/differential/harness/ that the suite needs, package.json and bun.lock (the devDependency only), docs/design/09-port-plan.md's "SDK suites" paragraph. Fixes in src/ for differences the suite finds are in scope when they are small (each in its own commit, in the module that owns the behavior, with a scenario or differential case at the endpoint level too); a difference that needs a larger change goes into the PR body and your reply for the lead to schedule, with the test kept as a pending (`test.todo`) case.
Depends on: M5.1, M5.2, M5.3 (merged).
Acceptance:
  - Every public method of every service in SDK 0.28.1 is called at least once against both servers, on copies of the shared fixture (or a fresh install where the fixture does not fit), and the normalized results (return values, thrown ClientResponseError status/response, realtime events received, files and emails produced) are compared with the harness's normalization. Services: RecordService (CRUD, list helpers, auth methods, password/OTP/OAuth2 code auth, refresh, impersonate, verification, password reset, email change, subscribe/unsubscribe), CollectionService (CRUD, import, scaffolds, truncate), SettingsService (getAll, update, testS3, testEmail, generateAppleClientSecret), LogService, BackupService (create, upload, list, download URL, delete, restore), CronService, FileService (getURL with thumbs, getToken and protected files), HealthService, RealtimeService, BatchService, and the AuthStore and `pb.send` behavior the methods rely on (auto-cancellation, filter() binding). Take the full method list from the SDK's types.
  - The PR body has a table: every SDK method → the test that calls it. A method that cannot run headless against both servers (for example the popup form of authWithOAuth2, which needs a browser window) is listed with the reason, and the closest method that does run is named (authWithOAuth2Code against the mock provider; the urlCallback form of authWithOAuth2 if it can be driven without a browser).
  - Mail-driven flows (verification, password reset, email change, OTP) read their tokens from Mailpit or the SMTP sink, as the existing suites do. S3 methods use the S3 test server. No external services, no real credentials.
  - Realtime: the SDK uses the global EventSource. Use Bun's if it works; otherwise a small test-only shim on fetch in test/support/. A new npm devDependency for it needs a reason in the PR body.
  - The suite runs in `bun run test:reference` (it lives under test/differential/, which `bun test` skips) and adds at most about 3 minutes to it. Timestamps, ids, tokens and file-name suffixes are normalized as the harness does; do not loosen the comparison beyond that.
  - Known differences listed in docs/design/04-api-compatibility.md and the hardening backlog are expected: assert them as listed, do not fix them here.
  - `bun run check` and `bun run test:reference` pass locally (D25). The flakes in the hardening backlog (`freePort()`, realtime cascade order, OAuth2 realtime order, and others listed there) are known; do not fix them here, and list any you saw in the PR with the rerun's result.
Out of scope: the Dart SDK and community SDKs; performance (M7.1); crash tests (M5.9); dashboard browser tests (M6.4).
Measurements: none, unless a fix changes the database access layer, filters, realtime or file handling (AGENTS.md: then before/after numbers in docs/perf/).
Notes from the lead:
  - Results are API output: status codes, error bodies and event payloads must be identical after normalization.
  - Branch: task/M5.8-sdk-suite. PR title: "M5.8: JavaScript SDK suite".
  - The host has limited memory: run `bun run check` and `bun run test:reference` one after the other, never in parallel, and never write into tracked fixtures.
  - There is no time limit; finish the task. Stop early only for a real blocker (a design conflict the lead must decide, or a usage/rate-limit error), and describe it in the PR and your reply.
```
