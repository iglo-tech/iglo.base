```text
Task M2.6: filter differential fuzzer
Goal: a seeded generator of random filters and sorts that runs each case against upstream v0.41.0 and iglo.base through `GET /api/collections/{c}/records` and proves that they return the same results, clean for 100,000 cases.
Read first: AGENTS.md, docs/design/12-work-plan.md (task M2.6, Rules for workers), docs/design/05-rules-and-filters.md (all of it), docs/design/10-decisions.md (D25, D26), test/differential/harness/ and test/differential/resolver/ plus test/differential/records-read/ (how both servers are started and fixtures are copied).
Upstream (v0.41.0, read only, for what the grammar and resolver accept): tools/search/filter.go, tools/search/identifier_macros.go, tools/search/token_functions.go, core/record_field_resolver*.go, apis/record_crud.go (list); fexpr v0.7.0 at /home/t3-code/upstream/fexpr.
Owns: test/differential/fuzz/ (new), a `fuzz:filters` script in package.json, docs/perf/M2.6-filter-fuzz.md, and fixes in src/search/ and src/resolver/ for real differences the fuzzer finds, each with a fixed regression case and in its own commit. A real difference anywhere else in src/: fix it in its own commit if it is small, and name it in the PR.
Depends on: M2.4 (merged).
Generator:
  - Deterministic from a seed: the same seed gives the same cases. Every failure prints seed, case number, request URL and token kind, so it can be replayed by one command.
  - Schema: upstream's fixture (test/fixtures/pocketbase) on a writable copy per server; add a generated collection set only if the fixture leaves a required form unreachable.
  - Covers: all operators and their any-of forms (`?=` etc.), `&&`/`||`/parentheses/nesting, every field type's values (matching, non-matching, wrong type, null, "", numbers as strings, bool, dates, escapes, `%` and `_` in `~`), dotted relations (single and multiple, nested), back-relations (`_via_`), modifiers (`:isset`, `:changed`, `:length`, `:each`, `:lower`) in filters, `@request.*` and `@collection.*` (with `:alias`), macros, `geoDistance()`, `strftime()`, and sorts including `@random`-free multi-field and `@rowid`.
  - Auth is random per case: guest, record user tokens of two collections, superuser (minted once per server and reused; never a real credential). Run across collections with different list rules, including null, "" and rule-with-relation.
  - Most cases are valid; about 10% are invalid, over-limit or unknown-field filters.
  - Macros have no injected clock in the upstream binary: the fixture's dates are far from now, so most macros are stable; exclude from comparison, or avoid, any macro form whose result can flip between the two calls (`@second`, `@minute` equalities against generated time values). State what was done in the report.
Comparison: status code; on success the record ids in order, `totalItems`, `totalPages`, `page`, `perPage` (compare id sets when the sort is ambiguous, and say how ambiguity is detected); on error the error body. Run page sizes and `skipTotal` randomly. After a failure the run continues and collects up to a bounded number of distinct failures.
Minimization: a shrinker reduces a failing filter to a smaller one that still differs. Each real difference that is fixed gets its minimized case in a fixed suite in test/differential/fuzz/, which `bun run test:reference` runs together with a short fuzz of about 500 cases (fixed seed, under about 60 s).
Acceptance:
  - `bun run fuzz:filters -- --seed <n> --cases 100000` finishes with zero unexplained differences. Differences that D26 covers (hand-crafted input handled safely) may be listed as named, narrow exclusions in the fuzzer with a reason, and go into the PR body for the lead to judge; a difference a real client filter can hit is fixed, never excluded. Rule bypass or a leak of hidden data is always a fix.
  - Run it at least twice with different seeds; the seeds, durations and case mix go in docs/perf/M2.6-filter-fuzz.md. Keep the report short.
  - `bun run check` and `bun run test:reference` pass locally.
Out of scope: writes, expand and `fields` beyond what a filter needs, rate limits (M4.8), performance work, refactors, changes to the harness's contract (additive helpers are fine).
Measurements: docs/perf/M2.6-filter-fuzz.md; a change to src/search or src/resolver with a fix also states its before/after cost for one representative filter there.
Notes from the lead:
  - The host has limited memory and its swap is full. Keep concurrency at 4 requests per server at most; run the 100,000 cases in the foreground under `nice`; do not run them alongside `bun run check`. Both servers run from a temp directory, removed afterwards. Do not raise a memory limit.
  - Branch: task/M2.6-filter-fuzz. PR title: "M2.6: filter differential fuzzer".
  - There is no time limit; finish the task. Stop early only for a real blocker (a design conflict the lead must decide, or a usage/rate-limit error), and describe it in the PR and your reply.
```
