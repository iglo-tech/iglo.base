# Brief M5.2

Written by the chief of staff on 2026-10-30 from the work plan's template. It applies the M0.7 answer (D10, `docs/perf/M0.7-thumbnails.md` → "What M5.2 must do").

```text
Task M5.2: Files endpoint, file tokens, protected files, thumbnails
Goal: serve record files on `/api/files` exactly as upstream v0.41.0 does (file tokens, protected files, headers, ranges, downloads, thumbnails generated and cached in pb_data/storage the way upstream stores them), with bounded memory.
Read first: AGENTS.md, docs/design/10-decisions.md (D5, D8, D10, D24, D25, D26), docs/design/07-files-mail-backups-jobs.md, docs/design/03-data-compatibility.md (storage layout), docs/design/04-api-compatibility.md, docs/design/02-architecture.md (files/, tools/filesystem, thumbnails worker pool), docs/design/12-work-plan.md (M5.2, Rules for workers), docs/perf/M0.7-thumbnails.md (the whole "Answer" section is a requirement list) and scripts/spikes/M0.7/ (orient.ts, imaging.ts, gif.ts, png.ts, thumb.ts, candidates/bun-imaging.ts, candidates/bun-hybrid.ts: port these into src/, do not import from scripts/), and the code it builds on: src/tools/filesystem/, src/records/record-tokens.ts (file tokens), src/apis/base.ts, src/apis/record-crud.ts, src/server/.
Upstream (v0.41.0, .upstream/pocketbase or /home/t3-code/upstream/pocketbase, read only):
  - apis/file.go (bindFileApi, fileToken, download: protected files and the token check, `thumb`, `download` query, imageContentTypes, defaultThumbSizes, the singleflight + semaphore, PB_THUMBS_MAX_WORKERS / PB_THUMBS_MAX_WAIT / PB_THUMBS_MAX_SOURCE_PIXELS, serving the original on failure).
  - tools/filesystem/filesystem.go: Serve (headers: Content-Type from attrs, Content-Disposition inline/attachment rules and the inline-safe types list, Content-Security-Policy, X-Frame-Options/`X-Content-Type-Options` as upstream sets them, Cache-Control, ETag/Last-Modified/Range/If-* through http.ServeContent semantics) and CreateThumb/createThumb (size modes, content type per source format, thumb key layout `thumbs_<name>/<size>_<name>`).
  - disintegration/imaging and golang.org/x/image as already ported in the spike; Go's image.DecodeConfig port in orient.ts.
  - Tests: apis/file_test.go (all 28 named scenarios, as data-driven scenarios; drop only hook-event expectations and list them) and the Serve/CreateThumb cases of tools/filesystem/filesystem_test.go.
Owns: src/files/ (new: the file API handler, thumbnail generation, worker pool and worker entry), the route registration for /api/files in the server wiring (own commit, named), the Serve/CreateThumb parts of src/tools/filesystem/, the build entry for the thumbnail worker in package.json's build script if a separate worker file must be compiled in (as src/db/read-worker.ts is), LICENSE (append the disintegration/imaging MIT and Go / golang.org/x/image BSD-3-Clause notices), test/files/ (new), test/scenarios for files, test/differential/files/ (extend), docs/perf/M5.2-*.md, and the files/Thumbnails lines in docs/design/02-architecture.md and 07-files-mail-backups-jobs.md.
Depends on: M3.2, M0.7 (merged).
Acceptance:
  - All 28 apis/file_test.go scenarios pass against both servers in `bun run test:reference` and against iglo.base alone in `bun test`, on copies of the vendored fixture.
  - Differential cases (at least 25) beyond the scenarios: public and protected files with and without a valid, expired or wrong-collection file token; superuser and auth tokens for protected files; `download=1` and the Content-Disposition/Content-Type/CSP headers for image, svg, html, pdf and unknown types; Range and If-None-Match/If-Modified-Since requests; missing record, file not in the record, file not on disk; every thumb size mode (WxH, WxHt, WxHb, WxHf, 0xH, Wx0, 0x0 and an unlisted size → original) for JPEG (incl. Exif orientations 1–8), PNG, GIF, WebP; non-thumbable types (tiff, bmp, svg) get the original; corrupt image and over-the-pixel-limit original (served original); a thumb cached by upstream is served by iglo.base and the reverse (same key, same content type); compare thumbs by dimensions, content type and mean absolute error per channel with the tolerance the M0.7 report measured (lossy WebP ~8/255).
  - The M0.7 compatibility set re-run against upstream through the HTTP API, results in docs/perf/M5.2-files.md.
  - Memory: peak RSS for a 50 MP JPEG thumb at concurrency 1 and 4 (bounded, one measurement at a time, watch MemAvailable) and for serving a 160 MiB file (streamed, not buffered), recorded in docs/perf/M5.2-files.md with upstream's numbers.
  - Thumbnail work runs off the main thread in lazily started Bun Workers, bounded by the semaphore; no thumb generation inside a database transaction; no process-global state (the pool belongs to the app context).
  - `bun run build` produces one executable that generates thumbs (the worker is compiled in); the test suite exercises the compiled executable.
  - `bun run check` and `bun run test:reference` pass locally (D25).
Out of scope: S3 file serving (M5.4; keep the storage calls behind the existing System so M5.4 adds a driver), backups (M5.3), the dashboard's file screens (they use the endpoint as-is), pixel-exact lossy WebP (D10 backlog), the damaged-file differences already in the hardening backlog.
Notes from the lead:
  - Thumb files and their `.attrs` are data contract: same path, same content type and metadata as upstream writes.
  - Serving the original on any thumb error matches upstream; the error goes to the app log only as upstream logs it (no informational console output).
  - The host has limited memory and a small disk: run `bun run check` and `bun run test:reference` one after the other, never in parallel; keep large-file tests bounded and generated, delete generated data, never write into tracked fixtures.
  - Branch: task/M5.2-files. PR title: "M5.2: Files endpoint, file tokens, protected files, thumbnails".
  - There is no time limit; finish the task. Stop early only for a real blocker (a design conflict the lead must decide, or a usage/rate-limit error), and describe it in the PR and your reply.
```
