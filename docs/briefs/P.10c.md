# P.10c State fixes: storage

Written by the lead on 2026-11-06 (owner request) from a read-only audit of implicit state machines. Each item names where the state lives, the reported defect and the intended fix. The audit read the code but did not run it: **confirm each item on main first**, and compare with upstream v0.41.0. If an item does not reproduce, or the fix would change what upstream answers to a real client's request, leave it and say why in the PR (D26). Every fix gets a test through a public boundary (HTTP, files on disk, the S3 test server, `pb_data` read back by upstream) where one exists; latent items with no public boundary may go in without a dedicated test; say which.

Owns: `src/db/`, `src/tools/filesystem/`, `src/tools/archive/`, `src/files/`, `src/oauth2/safe-file.ts`, `src/fields/file.ts` and their tests. `src/db` is a shared contract (work plan): keep its public shape; this task is the lead-approved change to it.

## Items

1. **Transaction done-flag vs SQLite** (`src/db/dbx/tx.ts:44-121`). If SQLite rolls the transaction back on its own (SQLITE_FULL, IOERR, interrupt; see the comment at `:116-117`), `done` stays false. Code that catches the error and carries on then runs each later statement in autocommit, so those writes commit one by one; the final COMMIT fails and `onComplete` (`src/db/db.ts:177-184`) marks the models new although rows were committed. Fix: `exec`/`query`/`prepare` refuse when `conn.inTransaction` is false while `done` is false (throw the same error kind a done transaction gives). Measure: this is the db hot path, so put before/after numbers for a write-heavy and a read-in-transaction benchmark in `docs/perf/P.10c-tx-state.md`.
2. **S3 multipart upload** (`src/tools/filesystem/internal/s3blob/s3/uploader.ts:81-249`, `s3.ts:163`). If parsing the init response fails after S3 created the upload, no abort runs and the upload is orphaned; an empty `UploadId` is accepted and sent as `uploadId=`; an empty part ETag is sent in the Complete XML; a 200 Complete whose body is an `<Error>` is not checked; requests use `timeout: false` and the signal is optional, so a stalled part never reaches the abort. Fix: abort whenever an upload id is known; reject an empty UploadId or ETag as an error; parse the Complete response for `<Error>`; give every upload request a bounded signal when the caller passes none (match the timeouts upstream's S3 client uses). Test against the S3 test server where possible.
3. **Zip writer and reader closed state** (`src/tools/archive/zip-writer.ts:158/180/258/319/370`, `zip-reader.ts:135`). `addFile`/`addOpenFile`/`#write` and `ZipReader.close`/`copyTo` do not check a closed state, so a call after close or abort writes to or closes an fd the OS may have reused. Fix: closed guards that throw. In `#inflate` (`zip-reader.ts:418-482`) make sure the `ended` promise cannot reject unhandled.
4. **Writer leaked when an upload generator stops early** (`src/tools/filesystem/filesystem.ts:289-315`). `uploadFileSteps` cancels the writer only in `catch`; `.return()` or a `break` in the consumer leaves the temp fd and `.tmp` file. Fix: `finally` cancels the writer unless it was closed. Also `fileblob.ts:543-610`: overwriting an existing blob writes the `.attrs` sidecar before the rename and deletes it if the rename fails, leaving the old blob without attrs. Check upstream's order; fix only if upstream keeps the old attrs.
5. **Thumb pool close** (`src/files/thumb-pool.ts:159-183`). `close()` does not reject queued `#waiters`, so they wait out `maxWaitMs` (60 s); `render` spawns a worker whenever no slot is idle without enforcing `maxWorkers` itself. Fix both inside the pool.
6. **`safeFetch` redirect limit** (`src/oauth2/safe-file.ts:197-214`). It throws "stopped after 10 redirects" before `res.body?.cancel()`, leaving the last body open. Cancel first.
7. **Pending file state after a failed transaction** (`src/fields/file.ts:424-744`, `src/records/record-save.ts:623-664`; read `record-save.ts`, change it only if needed and say so). (a) Inside a transaction, after a successful write the field value is already file names; if the transaction then fails, `deleteNewlyUploadedFiles` removes those files and `markAsNew` runs, but the Record still holds the names, so saving the same object again references missing files. (b) With a transactional parent (a data transaction inside a migration's aux transaction) the error path fires with `parent` while `isTransactional()` is true, so cleanup is skipped (`file.ts:424`) and uploads are orphaned. Compare with upstream's `core/field_file.go` and `core/db.go`; fix what upstream does not share, and record the rest in the PR.
