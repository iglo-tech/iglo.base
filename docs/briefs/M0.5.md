Task M0.5: Differential harness and scenario format
Goal: a scenario format for upstream's API table tests and a harness that runs each scenario against upstream v0.41.0 and iglo.base on separate copies of a fixture, normalizes and compares the responses, and also runs the same scenarios against iglo.base alone (with upstream's own expectations) in plain `bun test`, starting with upstream's 3 health scenarios.
Read first: AGENTS.md, docs/design/09-port-plan.md (Reference tools, Differential suite), docs/design/04-api-compatibility.md (Deliberate differences), docs/design/03-data-compatibility.md (Verification), docs/design/12-work-plan.md (Shared contracts, Rules for workers), docs/briefs/M0.2.md, and the existing helpers in test/support/ (upstream.ts, executable.ts, child.ts, reference-tools.ts) and test/differential/db/fixture.ts.
Upstream (v0.41.0, .upstream/pocketbase after `bun run upstream:prepare`, or /home/t3-code/upstream/pocketbase):
  - tests/api.go (ApiScenario: Name, Method, URL, Body, Headers, Delay, Timeout, ExpectedStatus, ExpectedContent, NotExpectedContent, ExpectedEvents; how Test() checks status and content, including the "*" and empty-content conventions and how the body is compared) and tests/app.go (NewTestApp: the fixture is copied from tests/data for every scenario; read for the copy semantics only, the Go hooks are not ported).
  - apis/health_test.go: the 3 scenarios to port.
  - tests/data/: the fixture (data.db, auxiliary.db, storage/; about 700 KB).
Owns: test/scenarios/ (the scenario type, the health scenarios as a typed TypeScript data module, and the runner that runs them against iglo.base alone), test/differential/harness/ (fixture copies, starting both servers on them, sending requests, normalizing, comparing, reporting), test/differential/scenarios.test.ts, test/fixtures/pocketbase/ (vendored copy of upstream's tests/data, see notes), and the Differential suite section of docs/design/09-port-plan.md (describe the format as built). Small changes to test/support/ helpers if the harness needs them (for example starting iglo.base or upstream on a given pb_data directory).
Depends on: M0.2, M0.3 (merged). M0.4 is merged too, but iglo.base does not open pb_data in `serve` yet (that comes with M1.2).
Acceptance:
  - The scenario format covers every ApiScenario field except ExpectedEvents (dropped, as the design says), plus: an optional prepare step for the fixture copy (later tasks port BeforeTestFunc and TestAppFactory into it), a `pending` marker (task id and reason) for a scenario that iglo.base cannot pass yet, and a `difference` marker that names an entry in 04-api-compatibility.md's Deliberate differences. A pending scenario must still run and must fail its comparison: the run reports it, and the test fails once it starts to pass, so the marker is removed by the task that fixes it.
  - Differential mode (`bun run test:reference`): the 3 health scenarios run against both servers, each on its own fresh copy of the fixture. Status, headers that matter (content-type and upstream's security headers) and bodies are compared after normalization. The normalization rules are written down in the harness: IDs, tokens and timestamps compared by format, JSON compared structurally except `json` field values compared as raw bytes. Hooks for later tasks to add rules are code in the harness, not configuration. The superuser health scenario is marked pending on M2.3 (the superuser fields of /api/health come with auth; see docs/status.md); guest and regular user pass.
  - Upstream-expectation mode (plain `bun test`, so it runs in the CI `check` job with no network): the same scenarios run against the compiled iglo.base executable on a copy of the vendored fixture, checking upstream's ExpectedStatus, ExpectedContent and NotExpectedContent exactly as tests/api.go does; the pending marker applies here too.
  - Every scenario also passes against the upstream binary in differential mode, which confirms that the ported expectations describe real upstream behavior.
  - The vendored fixture matches upstream: a `test:reference` test compares test/fixtures/pocketbase/ byte for byte with .upstream/pocketbase/tests/data. Tests only ever use copies; the vendored files are never written.
  - `bun run check` and `bun run test:reference` pass locally and in CI, on Linux and macOS.
Out of scope: porting other scenario files (each area's task ports its own), realtime subscriptions in scenarios (M5.1 extends the format), the data round-trip suite (M1.2 and later), the SDK suite, the filter fuzzer (M2.6), any change to src/.
Measurements: none (no db, filter, realtime or file handling change).

  - Scenario data is typed TypeScript (test/scenarios/<area>.ts exporting the scenarios), not JSON. Keep upstream's scenario names verbatim so a scenario can be found in the Go file.
  - The tokens in the health scenarios are upstream's fixture tokens (expiry in 2050). They are test data, not credentials.

  - Keep the harness small and readable. Later tasks add hundreds of scenarios to it, so the format is a shared contract: changes to it after this task go through the lead.
