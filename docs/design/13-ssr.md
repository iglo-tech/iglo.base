# SSR out of the box

Task P.13, owner direction 2026-11-07. Decision record: [D38](10-decisions.md#d38-ssr-in-the-sdk). iglo.base and its SDK (`iglo.base` on npm, D36) work with any JavaScript SSR framework without users solving the problems PocketBase leaves to them ([docs](https://pocketbase.io/docs/how-to-use/#why-not-js-ssr), [discussion #5313](https://github.com/pocketbase/pocketbase/discussions/5313)). Everything is in the SDK; the server's API stays PocketBase v0.41.0's.

## Sources

Read for this design (2026-11-07): PocketBase discussion #5313; the source of `@supabase/ssr` 0.12.7 and `@convex-dev/auth` 0.0.96 (Next.js server part); the docs of Appwrite SSR, Firebase session cookies, Clerk, Better Auth, Lucia and Auth.js (a Gemini research report, spot-checked by the lead). Upstream PocketBase v0.41.0 for the token model (`core/record_tokens.go`, `apis/record_auth_impersonate.go`).

| | Supabase | Convex Auth | Appwrite | Taken here |
|---|---|---|---|---|
| Client per request | `createServerClient` on cookie `getAll`/`setAll` | middleware + token helper | session client per request, admin client apart | the cookie adapter shape and the split between user and admin clients |
| Cookie | readable by JS, Lax, chunked | HttpOnly, Lax, `__Host-` | HttpOnly | HttpOnly, Lax, `__Host-` outside localhost |
| Refresh | middleware; rotating refresh tokens | middleware, when under 10 % of the lifetime | sliding | sliding at half the lifetime, in middleware |
| Browser | token read from the cookie | page gets the access token at render; the refresh token never leaves the server | short JWT minted by the server | a short token minted by the server, handed over at render |
| Caching, CSRF | `Cache-Control: private, no-store` with every cookie write | cross-origin requests lose their cookies | SameSite | both |

## What makes iglo.base easier

- **Refresh races are harmless.** Tokens are stateless JWTs. `auth-refresh` issues a new token and the old one stays valid until it expires, so parallel requests that refresh the same session cannot log the user out (Supabase needs a grace window for its rotating refresh tokens). The SDK still sends one refresh per session at a time.
- **Every API call validates the token.** A revoked token (password change, `tokenKey` change, deleted record) gets 401 on the next call. An explicit check is only needed when a page has to know who is signed in without making any other call.
- **Short browser tokens exist already.** `POST /api/collections/{c}/impersonate/{id}` with `duration` returns a non-refreshable token (`NewStaticAuthToken`). A superuser client on the app server mints one per page, so the long-lived session never reaches page JavaScript and no new endpoint is needed.

## Design

### Clients

- `createServerClient({ url, cookies, origin?, request?, secure?, sessionCache?, cookieName?, cookieOptions?, readableCookie?, fetch?, clock?, lang? })` from `iglo.base/ssr`: a new SDK instance for one request, resumed from the request's session cookie. `autoCancellation` is off. Every request is sent with `cache: "no-store"`, applied at the fetch layer after `beforeSend` (so an app that replaces `pb.beforeSend` cannot drop it, and Next.js never caches server client responses). It is never reused across requests.
- `createSuperuserClient({ url, email, password })` or `({ url, token })` (an API key from `impersonate`): one long-lived instance per process, held in memory, `autoCancellation` off, refreshed before its token expires (upstream's `autoRefreshThreshold`). With email and password, a rejected refresh re-authenticates with the password; a client built from a token alone cannot. A token that is not refreshable (`refreshable: false`, as `impersonate` issues) is never sent to `auth-refresh`, which the server answers with 403: its requests carry it until it expires, then fail with the server's 401, and the app creates a new client with a new token. It provides one method, `impersonate(collectionOrRecord, recordIdOrDuration?, duration?)`, which mints a short user token (default 900 s, 15 minutes) for page JavaScript and realtime, never for serving user requests.
- **One SDK copy.** `iglo.base/ssr` imports `Client`, `ClientResponseError` and `BaseAuthStore` from the main entry (`iglo.base`) instead of bundling its own. `instanceof ClientResponseError` and `instanceof PocketBase` therefore agree across both entries (checked by `sdk:check-package`).
- `iglo.base/ssr` is server-only: its package `exports` maps the `browser` condition to a module that throws with a clear message. A named import of it fails the build in most bundlers (Turbopack, Bun); webpack only warns, and the app then throws on every request (see "Runtime (Next.js)").
- **Server-side sign-in and sign-out:** Every auth change the app makes on a server client's `authStore` (`authWithPassword`, `authWithOAuth2Code`, `authRefresh`, `authStore.save()`, `authStore.clear()`) writes or clears the session cookie through the adapter with `SSR_NO_CACHE_HEADERS`, and updates or evicts the session cache. A 401 from an ordinary data call never logs the user out; only the outcome of the session check decides session validity.
- **Session check:** `pb.auth.verify()` checks the session with iglo.base now, bypassing the cache, and throws the error when the session is not valid. It is the only name for the check; the SDK adds no other.

### Session cookie

- One cookie, `pb_auth` by default, written by the existing `exportToCookie`: the token and the user record (owner, 2026-11-07: pages read the user without a request). `exportToCookie` keeps upstream's fallback to the minimal record fields when the value would exceed 4,096 bytes.
- Defaults: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` and the `__Host-` prefix except on `localhost`, `127.0.0.1` and `::1` over http; `Max-Age` from the token's `exp`. The one exception is the fallback without superuser credentials, `readableCookie: true`, where the cookie is written without `HttpOnly` (see "Browser client and realtime").
- Cookie security decisions follow the **application's own request**: `secure` if given, else the adapter's `isSecure` (the request adapter sets it from the request URL), else `origin`, else `request.url`. They never follow the iglo.base URL, so an https app talking to `http://127.0.0.1:8090` gets `__Host-pb_auth; Secure`, and a local http app talking to an https backend gets a plain, non-`Secure` `pb_auth`. With none of these given, the cookie is secure.
- `cookieOptions` cannot break the name rules: `cookieOptions.secure` picks the name (`__Host-` when true), and a `__Host-` cookie never carries a `Domain` or a path other than `/`.
- Reading takes only the name the cookie is written under for the origin: `__Host-pb_auth` on secure origins, `pb_auth` otherwise. Decision (2026-11-08): on https a plain `pb_auth` is never read, because a sibling subdomain can set it for the parent domain, and the SSR client is unreleased, so no older cookie needs to keep working. When the session ends, both names are cleared on secure origins; the plain one is only removed, never read there.
- The record is used only when its `id` matches the token's `id`. A cookie can be edited by its user.
- The cookie value is decoded at most once per candidate. Adapters may return it decoded (the request adapter does) or as the browser sent it (Next.js does); the SDK tries the raw text first, then the percent-decoded text.
- Every response of a request that carries user data also gets `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`, `Expires: 0`, and `Pragma: no-cache` (`SSR_NO_CACHE_HEADERS`), so a CDN cannot hand one user's cookie or token to another (from Supabase). A request carries user data when it has a session cookie (either name), when it writes a cookie, or when it mints a browser token. Anonymous requests that write nothing keep their responses cacheable. Framework by framework, see "Response headers".
- A throwing `setAll` (Next.js Server Components are read-only) never rejects the request: the cookie write is skipped and the request continues.

### Session cache, check and refresh

No request re-authenticates by default (owner, 2026-11-07). Per server process:

- A bounded in-memory cache, `createSessionCache({ ttl, maxEntries, clock })`, created explicitly and passed to each `createServerClient` (no module global). It is keyed by a SHA-256 hash of the token (Web Crypto; the raw token is never a key), holds the user record and when the session was last checked, and holds the learned token lifetimes and the clock offset. Defaults: `ttl` 300 000 ms (5 minutes), `maxEntries` 10,000 (least recently used dropped first). `ttl` is in milliseconds. Cache operations run in call order, so a write started by an auth change is visible to the next read.
- **Lifetime learning:** tokens have an `exp` claim and no `iat` claim. A successful session response teaches the cache the collection's lifetime: `auth-with-password`, `auth-with-otp`, `auth-with-oauth2` and `auth-refresh` (the refresh the check makes included), when the token has `type: "auth"`, is refreshable, and names the record in the response. The lifetime is `exp − serverNow`, with `serverNow` from the response's `Date` header. Other responses that carry a token do not teach it: `files/token` returns a 180-second file token, and `impersonate` returns a non-refreshable token. Lifetimes are kept per collection ID in the cache. Until a collection's lifetime is known, the first check of its session refreshes once to learn it. The SDK never assumes a fixed lifetime.
- A request whose token is in the cache, was checked within `ttl`, and has at least half its learned lifetime remaining uses the cached record with no request to iglo.base.
- Otherwise the SDK calls `auth-refresh` once. Parallel requests for the same token share that one request (single-flight). The shared flight returns a plain outcome, `{ kind: "ok", token, record } | { kind: "revoked", error } | { kind: "transient", error }`, and each waiting request applies it to its own client, auth store and cookie adapter:
  - `ok`: updates its auth store and the cache entry; writes the cookie when the token changed.
  - `revoked` (401, 403, 404): clears its session, evicts the cache entry and writes cleared cookies. `pb.auth.verify()` throws the error; an ordinary request continues signed out.
  - `transient` (network error or 5xx): keeps its session, does not touch the cookie or the cache. `pb.auth.verify()` throws the error to its own caller only; an ordinary request is not affected by another caller's `verify()`.
- Expiry checks allow 60 seconds of clock skew. The SDK corrects for the difference between the app server's clock and iglo.base's `Date` header, learned from each response and kept in the cache, so an app clock that is minutes off does not drop a session the server still accepts.
- Before the first response in a process the offset is unknown and counts as 0; the 60-second allowance still applies. So until then, an app clock more than 60 seconds fast can drop, without a request, a session whose token is close to its `exp` that iglo.base still accepts. The first response corrects the offset.
- Trade-off: between checks, a revoked session can still render as signed in for up to `ttl`. Data calls are not affected: iglo.base rejects the revoked token on every API call, as a guest.

### Browser client and realtime

Built in P.13d. The code is `sdk/src/ssr/browser-token.ts` (minting), `renew.ts` (the renew route) and `browser-client.ts` (the browser entry, `iglo.base/ssr/browser`).

- **Minting at render.** `mintBrowserToken(serverClient, superuser?, { duration? })` takes the server client after its session is resumed, and returns `{ token, record, expiresAt, serverTime }` (`expiresAt` and `serverTime` in milliseconds) or `null` when nobody is signed in. The token comes from `superuser.impersonate` (900 s by default). `serverTime` is iglo.base's clock as the minting client last read it from a `Date` header (`superuser.serverNow()`, or `serverClient.serverNow()` in fallback mode): the browser client measures its own clock against it. The record is the server client's own, never data from the request. The answer is per user: whatever response carries it must be `Cache-Control: private, no-store` (`SSR_NO_CACHE_HEADERS`). Each adapter's `pbBrowserToken` marks the request, so the response that carries the token gets the headers (see "Response headers"). It lives in the server entry, not the browser entry, because it needs the session and the superuser client, and neither may reach a browser bundle. Without superuser credentials it answers the session token itself, and only in fallback mode.
- **Renew route.** `handleBrowserTokenRenew(request, options)` is the adapter route: `POST` only, Origin-checked always, and every answer carries `SSR_NO_CACHE_HEADERS`. It resumes the session with `createServerClient` and then checks it with iglo.base (`auth.verify()`), so a session revoked since its last check is refused even while the session cache holds it. Its answers: `200 { token, record, expiresAt, serverTime }` with a fresh minted token, `401` (no valid session; the cookies are cleared when iglo.base revoked it, or when impersonate answers 404, which means the user was deleted after the check), `403` (foreign origin), `405` (not `POST`, with `Allow: POST`) and `503` (iglo.base unreachable, or impersonate answering 401 or 403, which means the superuser credentials were refused (missing, expired, revoked, or not a superuser's), or failing for another reason). A `503` keeps the session cookie: a refused superuser credential is an operator's problem and says nothing about the user's session, so it must not sign every user out. The browser client keeps its token and retries. A missing configuration (no superuser client and no `readableCookie`) throws before the session is checked or any request is made. Configuration errors are not answered: they throw.
- **Browser client.** `createBrowserClient({ url, token?, record?, serverTime?, renewUrl?, handOffUrl?, cookieName?, clock?, timers?, fetch?, lang? })` returns a `BrowserClient`, a subclass of the SDK `Client` that the main entry provides. Its auth store is seeded from the token and the record (the record is dropped when its id is not the token's). Pass `serverTime` with the token: the client then knows the device clock's offset from the start. Without it the offset is learned from the first renewal answer. Without a token, it reads the readable session cookie (fallback), under the name the server writes for the page's scheme: `__Host-pb_auth` on https, `pb_auth` otherwise.
- **Clock.** Every lifetime is measured on iglo.base's clock: the expiry is `exp` from the token, the current time is this device's clock plus the offset from `serverTime` (at the page's render) or from each renewal answer. A device clock that is minutes fast or slow therefore changes neither when the token renews nor when it is treated as expired.
- **Renewal policy.** It renews when half of the remaining lifetime is left, and never less than 60 s before `exp`. Successful renewals are at least 30 s apart, whatever the lifetime or the clocks say, so a token that lives under a minute cannot make the client renew in a loop. `renew()` shares one request between parallel callers and the timers. Outcomes: `200` stores the token and reschedules; `401` clears the store; a network error or `5xx` keeps the token and retries with a backoff of 1 s doubling to 30 s, at most ten times in a row; after that, or once no retry fits before `exp`, the store is cleared at `exp`; other `4xx` (a route that is missing or refuses the origin) keep the token and do not retry. A renewal whose session changed while it was in flight (a sign-out or another sign-in) is discarded. Every timer delay is at most 2^31 − 1 ms (`setTimeout`'s maximum, about 24.8 days): a longer wait is re-armed when it fires, so no delay is cut short. `dispose()` stops the timers. The clock and the timers are injected, so tests run without sleeping.
- **Realtime.** Upstream keeps each realtime client's auth on the server (`apis/realtime.go`). `realtimeSetSubscriptions` accepts a change of token only for the same record (`isSameAuth`: same id and collection) and answers `403` to any other change, including a sign-out, while the old auth stays in place. A password or `tokenKey` change unsets it. The browser client therefore compares the identity of each new auth store token (collection and id, or guest) with the one its realtime connection was last authorized for. The same identity: `RealtimeService.resubmit()` sends the subscriptions with the new token on the same connection, so subscriptions keep receiving events across a renewal. A different identity, a sign-out, or a sign-in from guest: `RealtimeService.reconnect()` closes the connection and opens a new one with the same subscriptions, and the new client ID is authorized with the current token, or as a guest. The new connection retries like a dropped one: its first attempt waits the first backoff step, and a failed attempt retries in the background with the usual backoff, so an outage during the change does not end realtime. It does not call `onDisconnect`, which means a network or server error, since the change was intended. Both are in the SDK's realtime service and are its only additions. A change of user while a new connection's first subscription request is in flight is the same case: the request is cancelled with the connection, and the continuations of the closed connection do nothing, so the connection that replaces it restores the subscriptions with the current authorization. A sign-out in another tab is noticed at the next renewal, which the session check refuses (`401`).
- **Hand-off.** `handOff()` posts the popup token (from `authWithOAuth2()`) to `handOffUrl` (`handlePopupHandOff`), then renews, so the long-lived popup token leaves page memory. On any failure, whatever its status (a network error, a `401`, `403`, `5xx`, or a failed renewal), the popup token is cleared from the store and the error is thrown.
- **Fallback without superuser credentials.** `createServerClient({ readableCookie: true })` writes the session cookie without `HttpOnly` (every write and clear of it, including the popup hand-off). `mintBrowserToken` and `handleBrowserTokenRenew` then answer from the session itself, without `impersonate`, and the browser client reads the cookie. This is weaker against XSS: any script on the page can read the session token for as long as the session lasts. Documented in the SDK README and in D38.
- **Trade-off.** A browser token minted at render takes the session check from the server client, which uses the session cache, so a session revoked within the cache TTL can be minted a token once more. The next renewal of that page (within half of the token's life, 7.5 minutes by default) checks with iglo.base and ends it. Data calls are unaffected throughout.

### OAuth2

- **Redirect flow, server only.** Two methods on `ServerClient` (they use the client's cookie rules and its auth collection, and add no module state):
  - `pb.startOAuth2(provider, { callbackUrl, redirectTo?, collection? })` reads `listAuthMethods` for the auth collection (default `users`) and finds the provider. It writes a 10-minute temporary cookie `pb_oauth2` (`__Host-pb_oauth2` outside localhost; `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=600`, no `Domain`) holding `state`, the PKCE `codeVerifier`, the provider, the collection, the callback URL and `redirectTo`. It returns the server's `authURL` with `redirect_uri` set to `callbackUrl`, so the caller redirects with `Response` and applies the adapter's cookies to it. `callbackUrl` is required (an absolute http(s) URL): it is the redirect URI registered with the provider, and it is stored so the code exchange sends the same one. Failures: `OAuth2Error` (`unknown-provider`, `unsupported-provider`, `invalid-callback`, `no-cookie-writer`) or the server's `ClientResponseError`.
  - `pb.completeOAuth2(request | url)` on the callback route reads `code`, `state` and `error`. It compares `state` with the cookie in constant time, rejects an expired cookie (`exp` inside the cookie), exchanges the code with `authWithOAuth2Code` (which writes the session cookie the usual way) and deletes the temporary cookie on every outcome. It returns `{ ok: true, redirectTo, auth }` or `{ ok: false, redirectTo, error }`, where `error` is an `OAuth2Error` (`missing-cookie`, `expired`, `state-mismatch`, `provider-error` with the provider's `error`, `missing-code`) or the server's `ClientResponseError` (a network failure is a `ClientResponseError` with status 0). Only failures the SDK cannot classify throw. On https only `__Host-pb_oauth2` is read; a plain `pb_oauth2` gives `missing-cookie`.
  - **Providers that return by POST.** Upstream sends Sign in with Apple `response_mode=form_post`, so Apple returns to the callback as a cross-site POST. The browser does not send the `SameSite=Lax` temporary cookie with it, and the callback reads only the query string, so the redirect flow cannot complete. `startOAuth2` refuses any provider whose `authURL` sets a `response_mode` other than `query` with `OAuth2Error` `unsupported-provider`, before it writes a cookie. Such a provider uses the popup flow: `authWithOAuth2()` in the browser, which upstream completes through its `/api/oauth2-redirect` POST route, then `handlePopupHandOff`.
  - `redirectTo` must be a same-origin path that starts with one `/`. `//host`, a backslash, a control character, a scheme or anything else that resolves to another origin becomes `/`. The stored value is checked again on completion.
  - **Binding, not signing.** The cookie is not signed. A signature would need a server-side secret, which this design does not have, and a second process would not share it. The state binding stops a stale or mismatched cookie from being used with another callback. On https the SDK reads only `__Host-pb_oauth2`, and a `__Host-` cookie can be set only by the app's own host (any port), so a sibling subdomain cannot plant a temporary cookie with its own state and verifier. A writer on that host can already set the session cookie. Over http the plain name is the only one read, so apps that serve the callback from http must treat the temporary cookie as writable by anyone who can write cookies for the host.
  - One temporary cookie per browser: a second sign-in started in another tab before the first completes replaces it, and the first fails with `state-mismatch`.
- **Popup flow:** the existing `authWithOAuth2()` in the browser (the only flow that takes Sign in with Apple's POST, see above), then the browser client posts the token to an adapter route. `handlePopupHandOff(request, options)` is that route's handler: `POST` only, the JSON body `{ token }`, same origin always (the Origin check runs with or without the session cookie). It checks the token with one `auth-refresh`, writes the HttpOnly session cookie from the refreshed token and record (the posted record is never read), and answers `200 { record }` with no token. A revoked token gets `401` and sets no cookie. This is Firebase's session-login pattern.

### CSRF

- `SameSite=Lax` on the session cookie and on the temporary OAuth2 cookie.
- `checkCsrf(request, { allowedOrigins?, cookieName? })` is the guard an adapter calls before its handler runs. It rejects `POST`, `PUT`, `PATCH` and `DELETE` requests that carry the session cookie (`__Host-pb_auth` or `pb_auth`, or the configured name) unless their origin is the request's own origin or one of `allowedOrigins`. The guard counts the session cookie under either name, because it does not know how the app named it (the app's `secure` setting is not visible to it): a stricter check, never a looser one. `Origin` decides; `Referer` is read only when `Origin` is absent. A request with neither header, or with `Origin: null`, is rejected too. Requests without a session cookie pass, and so do `GET`, `HEAD` and `OPTIONS`. A rejection returns `{ ok: false, reason, response }`, where `response` is a ready 403. `checkOrigin(request, allowedOrigins)` is the origin check alone.
- The request's own origin comes from the request URL. Behind a proxy that changes the public origin, list the public origin in `allowedOrigins`. `allowedOrigins` entries must be origins (no path); `checkCsrf` and `checkOrigin` validate them first, so an invalid entry throws on every call, including a GET or a request without a session cookie.
- The popup hand-off always runs `checkOrigin`, with or without the session cookie.
- Next.js Server Actions keep their own check.

### Adapter API (built in P.13e)

The shared part is `sdk/src/ssr/adapter.ts`; each adapter maps its framework's request, cookies and locals onto it, with no state of its own.

- **Options** (`AdapterOptions`): `url`, `sessionCache` (required: the app creates it), `superuser` (the app creates it; without it `readableCookie: true` is required, and the factory throws a `TypeError` otherwise, once, at creation), `origin` (the public origin, for the cookie security and the OAuth2 callback URL; default the request's origin), `secure`, `cookieName`, `cookieOptions`, `readableCookie`, `csrf` (`false` to opt out, or `{ allowedOrigins }`), `browserTokenDuration`, `routes`, `lang`, `clock`, `fetch`.
- **Routes** (`AdapterRoutes`, a route set to `false` is not mounted; defaults): `renew` `POST /api/pb/renew` (`handleBrowserTokenRenew`), `popup` `POST /api/pb/popup` (`handlePopupHandOff`), `oauth2Start` `GET /api/pb/oauth2/start/{provider}?redirectTo=` (a `302` to the provider, with the temporary cookie), `oauth2Callback` `GET /api/pb/oauth2/callback` (`completeOAuth2`: a `302` to `redirectTo`, with `oauth2_error=<kind>` added on failure, `server` for a `ClientResponseError`). A start that fails answers `404` (`unknown-provider`), `400` (`unsupported-provider`), `500` (`invalid-callback`, `no-cookie-writer`) or `502` (iglo.base refused). Unknown methods on a route get `405` with `Allow`.
- **Order per request:** the CSRF check (only requests that carry the session cookie, unless opted out), then the routes, then the session resume (`createServerClient` with the framework's cookies), then the app's handler. The renew and popup routes run their own Origin checks as well.
- **Cookie writes** go through each framework's own cookie API where it has one. Route answers carry their own `Set-Cookie` headers from the core. Every adapter runs one `NoStorePolicy` per request (`sdk/src/ssr/adapter.ts`): it is on when the request carries a session cookie, and turns on at the first cookie write or browser-token mint. Each adapter applies it to every response it returns, read after the app's handler has run.
- **Next.js** (`iglo.base/ssr/next`): `createNextAuth({ next, ... })`. It runs on the Node.js runtime only (see "Runtime" below). `next` is `NextResponse.next`, supplied by the app, since the SDK does not import `next/server`. `middleware(request)` writes the session cookies both onto the pass-through response and into the forwarded `Cookie` header, so Server Components see the refreshed session. It forwards the resolved cookie security as the request header `x-iglo-base-secure` (`1` or `0`) and drops any incoming copy first, so a client cannot set it. `serverSession({ cookies, headers })` reads that header, which decides the cookie names (`__Host-` or not) in a Server Component when `secure` is not configured; the cookie store there is read-only, so the refresh updates memory only.
- **SvelteKit**: `createSvelteKitAuth(options).handle({ event, resolve })` sets `event.locals.pb` (the `ServerClient`) and `event.locals.pbBrowserToken` (the browser-token function), and cookies go through `event.cookies.set`.
- **Nuxt**: `createNuxtAuth(options).middleware(event)` takes a structural event, not h3's: `method`, `path`, Node-style `headers`, `context`, a `setCookie` and `setHeader`, and an optional `readBody`. The app maps h3's functions onto it, so the SDK imports nothing from h3. It sets `event.context.pb` and `event.context.pbBrowserToken`. Nitro runs the handler after the middleware returns, so the policy calls `setHeader` as soon as it turns on: at once for a request with a session cookie, otherwise at the first cookie write or token mint in the handler. The origin is the option, else the `Host` header with `x-forwarded-proto`; behind no proxy, pass `origin`.
- **Astro**: `createAstroAuth(options).onRequest(context, next)` reads the cookies from the request's `Cookie` header (Astro's cookie store has no `getAll`) and writes them through `context.cookies.set`. It sets `context.locals.pb` and `context.locals.pbBrowserToken`.
- **React Router 7 and Remix**: `createReactRouterAuth(options).session(request)` returns `{ response }` when the CSRF check or a route answers, and otherwise `{ session, headers() }`. `headers()` builds the Set-Cookie and no-cache headers when it is called, so the route calls it last, as it builds its response: `data(value, { headers: headers() })` or `redirect(url, { headers: headers() })`. A sign-in or sign-out the handler made before the call is in the result; one made after the call is not, since the response is already built. The adapter cannot change a response that React Router has built. Every route module that calls `session()` re-exports `sessionHeaders` as its `headers` export, and so does every route module with an `ErrorBoundary`, at least `root.tsx` (the default template's only one): `export { sessionHeaders as headers } from "iglo.base/ssr/react-router"`. React Router builds the page's and the `.data` response's headers from that export. Without it, a route copies only the loader's and action's `Set-Cookie` lines, and the no-cache headers are lost (verified with `react-router@7.18.5` in framework mode: the HTML and single-fetch responses of a loader and of an action had no `Cache-Control`; with the export they have it). The boundary route needs the export because a session route that throws `data(…, { headers: headers() })` is rendered by the nearest boundary route, and React Router takes that response's headers from the boundary route, not the throwing one: its `headers` function gets them as `errorHeaders`. Without the export on the boundary route, the no-cache headers and the rotated cookie of the thrown response are lost (verified: `GET` of a thrown 403 had no `Cache-Control` until the root route exported `sessionHeaders`). `sessionHeaders` keeps the parent route's headers and adds the no-cache headers when the loader, the action or an error carries them, so on an anonymous request the root keeps the page cacheable. React Router appends the `Set-Cookie` lines itself. Route middleware would avoid the export, but in 7.18.5 it is behind the `future.v8_middleware` flag, so the adapter does not use it.

### Response headers

The no-cache headers (`SSR_NO_CACHE_HEADERS`) go on every response of a request that carries user data: a session cookie, a cookie write, or a minted browser token. How each framework gets them onto the response:

| Adapter | Where the headers are set | Limit |
|---|---|---|
| core (`iglo.base/ssr`) | the app adds `SSR_NO_CACHE_HEADERS` to its own `Response` | none: the app owns the response |
| `next` | the middleware's response (pass-through or answer), and Next.js's own headers for pages that read cookies | a Route Handler that changes the session sets them itself (below); Next.js sets its own `no-store` on Server Action responses |
| `sveltekit` | the response `resolve` returns, read after the handler | none |
| `nuxt` | `setHeader`, as soon as the policy turns on | none |
| `astro` | the response `next()` returns, read after the page renders | none |
| `react-router` | the route's `headers` export (`sessionHeaders`), which carries the `headers()` result into the page and `.data` responses; the root and every other route with an `ErrorBoundary` export it too, for a session route's thrown response | a route without the export loses them, and so does a boundary route without it; a response built before the `headers()` call does not get the cookies |
| all adapters, immutable headers | a response whose headers are immutable (a `fetch()` response in Node, or `Response.redirect()`) is sent as a copy with the same status, body and headers, plus the no-cache headers when they apply (`withMutableHeaders`, `NoStorePolicy.apply`) | `url` and `redirected` are not kept; an anonymous response is returned as it is; a network error (`Response.error()`, status 0) cannot be copied, so it is sent as it is, with or without a session |

**Next.js.** The adapter's own responses carry the headers as above. A page that reads the session reads cookies, so Next.js renders it dynamically, and Next.js sends `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` for it. The example's `/live`, `/protected` and `/api/me` show this in `test:examples`, which asserts `no-store` on them. Three things Next.js does not let the adapter do:

- **Server Components cannot set cookies or headers.** A refresh there updates memory only, and the page has no response of its own to mark. The middleware has already marked the request, and the page is dynamic.
- **A Route Handler that writes the session** (a sign-in or sign-out from a request without a session cookie) returns its own response. It must include `SSR_NO_CACHE_HEADERS` in it: `new Response(null, { status: 303, headers: { Location, ...SSR_NO_CACHE_HEADERS } })`. The example's `session/login` and `logout` routes do this.
- **A Server Action** is answered with `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` by Next.js itself, on every response (`next@16.4.5`, `app-render/action-handler.js`). That value replaces the middleware's on the action's response, so an action's response is never stored, with or without a session. The adapter adds nothing there, and a sign-in through a Server Action needs nothing else.

### Runtime (Next.js)

`iglo.base/ssr/next` runs on the Node.js runtime. Next.js 16 runs the middleware file `proxy.ts` on Node.js only, and the example uses it (`export function proxy`). Next.js 15.5 runs `middleware.ts` on the Edge runtime by default, so it needs `export const runtime = "nodejs"` in that file. The Edge runtime is not supported, and nothing guards against it: the package's `browser` condition resolves to the stub, which exports nothing, so the import fails. Observed with `next@16.4.5` and the example's code in a `middleware.ts` without the export:

- Turbopack (the default): `next build` fails with `Export createNextAuth doesn't exist in target module`, pointing at `iglo.base/dist/ssr-browser.es.mjs [middleware-edge]`.
- webpack (`next build --webpack`): the build passes with `Attempted import error` warnings, and every request answers `500` with the stub's message, `iglo.base/ssr is server-only and cannot be imported in browser code`, which names the Node.js runtime rule.

With `export const runtime = "nodejs"` the same `middleware.ts` builds under Turbopack and serves its pages. Next.js 15.5 itself was not run for this document.

## What is left out

- **Server changes.** iglo.base does not read auth cookies itself and gets no new endpoint (lead decision, 2026-11-07, D38).
- **JWKS or asymmetric tokens** for local verification: they would change the token format that PocketBase reads (data contract).
- **Cookie chunking:** with the minimal-record fallback the cookie stays under 4,096 bytes.
- **`auth-refresh` on every request,** as PocketBase's README examples do.
